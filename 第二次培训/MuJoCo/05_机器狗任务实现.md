# 机器狗任务实现

这一部分把前面已经跑通的 MuJoCo 基础真正放到完整四足模型上。任务目标仍然很具体：

```text
URDF
  ↓
转换并整理成 MJCF
  ↓
放入平坦场景
  ↓
12 个驱动关节配置 motor actuator
  ↓
设置合理的趴卧初始姿态
  ↓
data.ctrl[:] = 0.0
  ↓
运行并保持数值稳定
```

这一阶段手里已有一份真实机器人的 URDF，而 MuJoCo 最终要加载的是 MJCF。这里要完成的不是单纯“把文件格式换一下”，而是把原模型中的关节结构、几何和物理参数带到 MuJoCo 中，并确认转换后的模型仍然表示同一台机器人。

这一段按下面的顺序进行：

```text
读原始 URDF
    ↓
记下转换后必须保留的结构和参数
    ↓
用转换工具生成 MJCF
    ↓
把 MJCF 和原 URDF 对照
    ↓
交给 MuJoCo 加载、初始化和运行
```

## 从 URDF 得到一份可检查的 MuJoCo 模型

转换前先读原始 URDF，是因为转换后的 MJCF 需要有东西可以对照。对于腿部驱动关节，最先检查的是“哪两个刚体由哪个关节连接，以及关节沿什么轴运动”。

一个最小的旋转关节可以写成：

```xml
<robot name="mini_robot">
    <link name="base"/>
    <link name="thigh"/>

    <joint name="hip_joint" type="revolute">
        <parent link="base"/>
        <child link="thigh"/>
        <axis xyz="0 1 0"/>
        <limit lower="-1.0" upper="1.0" effort="20" velocity="5"/>
    </joint>
</robot>
```

这里记录的是：

```text
base
  ↓ hip_joint，绕 Y 轴转动
thigh
```

`parent` 和 `child` 给出关节连接的两个 `link`，`axis xyz="0 1 0"` 给出转轴；`lower`、`upper` 给出旋转关节的角度范围，单位为弧度。到了完整四足模型，12 个腿部驱动关节仍然要逐个保留这些关系。

URDF 里还会记录刚体的显示、碰撞和惯量信息，例如：

```xml
<link name="thigh">
    <visual>
        <geometry>
            <mesh filename="meshes/thigh.stl"/>
        </geometry>
    </visual>
</link>
```

后面核对转换结果时还会用到：

- `visual`：显示外形；
- `collision`：碰撞几何；
- `inertial`：质量、质心和惯量；
- `mesh filename`：外部网格文件路径。

拿到培训指定的机器人 URDF 后，先把 12 个腿部驱动关节整理成一张对照表：

```text
joint name        parent          child           axis
-----------------------------------------------------------
...               ...             ...             ...
```

这张表的用途不是整理笔记，而是转换完成后逐项检查 MJCF：关节有没有缺失，父子关系有没有改变，轴向有没有翻转或写错。

### 用 URDF Studio 完成格式转换

培训任务指定使用 [URDF Studio](https://urdf.enkeebot.com/zh/)。它是一个运行在浏览器里的机器人模型工作台，可以读取 URDF 及其网格资源，并把当前模型导出为 MJCF。

这个网站的导入、导出入口都在页面顶部的 **“文件”** 菜单中。对于带有 `meshes/` 等外部资源的机器人，不要只单独选择一个 URDF 文件；本任务直接导入包含 URDF 和资源文件的整个目录：

```text
文件
→ 导入文件夹
→ 选择培训提供的机器人模型目录
```

如果拿到的是已经打包好的 ZIP，也可以用“文件 → 导入文件”选择压缩包。页面也支持把文件夹或压缩包直接拖入。导入完成后，先确认目标 URDF 已经加载，并检查三维视图中没有明显缺失的 mesh。

然后从顶部菜单进入：

```text
文件
→ 导出
→ 导出格式：MJCF
```

MJCF 的导出窗口还有一组配置。按本次任务设置：

- **浮动基座：开启。** 这个选项会在根 body 上加入 `<freejoint/>`，让机器狗的机身在 MuJoCo 中能够自由平移和旋转；
- **包含执行器：关闭。** 网站默认会自动生成执行器，而且默认类型是位置执行器；本任务后面要自己给 12 个腿部关节配置 `motor actuator`，这里先不要让转换器替我们生成；
- **在 ZIP 中包含网格文件：开启。** 这样导出的 MJCF 和它引用的 mesh 会一起打包；
- **Mesh 目录：保持 `meshes/` 即可；网格格式保持“自动”。**
- 质量设置保持默认的自动模式，让已有质量、惯量继续保留；本任务不在这里重新估算整台机器人的质量参数。

最后点击 **“导出 ZIP”**。下载得到的不是单独一个 XML，而是一整个导出包；解压后把其中的 MJCF XML 和配套 mesh 一起放到自己的模型目录，再回到本地用 MuJoCo 检查。

所以这一段真正完成的是：

```text
URDF + mesh 目录
      ↓ 导入文件夹
URDF Studio 中的机器人模型
      ↓ 选择 MJCF 并设置导出选项
MJCF XML + mesh 导出包
      ↓ 解压
本地 MuJoCo 模型目录
```

转换工具负责把两种机器人描述格式之间的结构表示转换过去；导出成功还不能说明模型已经适合本次仿真。

导出以后，先用刚才记录的原始 URDF 信息核对：

- 12 个腿部驱动关节是否都还在；
- 每个关节连接的父、子刚体是否正确；
- 关节轴和运动范围是否对应原 URDF；
- 质量、惯量、碰撞几何是否保留下来；
- mesh 路径是否仍能找到实际资源。

这些关系检查通过，再进入 MuJoCo 本身的加载和运行检查。

### 转换以后先解决模型文件本身

先让转换后的机器人单独能够被 MuJoCo 打开：

```bash
python3 -m mujoco.viewer --mjcf=models/robot.xml
```

这一步只看模型本身：四条腿是否完整，前后左右是否明显错位，关节方向和范围能否对应原 URDF，机身是否具有自由基座，以及资源文件是否能找到。

真实机器人通常使用 STL、OBJ 等网格文件。MJCF 中会先声明资源：

```xml
<asset>
    <mesh name="body_mesh" file="body.stl"/>
</asset>
```

再由几何体引用：

```xml
<geom type="mesh" mesh="body_mesh"/>
```

如果网格统一放在一个目录，还可能看到：

```xml
<compiler meshdir="../meshes"/>
```

出现“mesh 找不到”时，顺着这三层检查：

```text
XML 在哪里
↓
compiler.meshdir 指向哪里
↓
asset 中 mesh.file 最终落到哪个真实文件
```

可以配合：

```bash
pwd
find . -type f | sort
```

确认真实目录结构。只移动 XML 而没有保持资源相对位置，很容易让转换后的模型失去网格文件。

## 读懂转换后的机器人在 MuJoCo 里怎样表示

模型能够打开以后，再用 Python 读取它：

```python
import mujoco

model = mujoco.MjModel.from_xml_path("models/robot.xml")
data = mujoco.MjData(model)

print("nq =", model.nq)
print("nv =", model.nv)
print("njnt =", model.njnt)
```

如果这台四足机器人由一个自由基座和 12 个单轴转动关节组成，那么：

```text
自由关节：qpos 7，qvel 6
12 个单轴转动关节：qpos 12，qvel 12
```

因此常见结果是：

```text
nq = 19
nv = 18
```

### 把名字、状态数组下标和执行器对应起来

真实模型里不能再依赖固定下标猜关节。先把全部关节名字列出来：

```python
for joint_id in range(model.njnt):
    name = mujoco.mj_id2name(
        model,
        mujoco.mjtObj.mjOBJ_JOINT,
        joint_id,
    )
    print(
        joint_id,
        name,
        model.jnt_qposadr[joint_id],
        model.jnt_dofadr[joint_id],
    )
```

把输出和刚才从 URDF 整理出的 12 个驱动关节逐一对上。这里有两次不同的映射：

```text
关节名称
→ mj_name2id(...)
→ joint id（MuJoCo 给这个关节的内部编号，用来索引 model.jnt_* 属性数组）

joint id
→ model.jnt_qposadr[joint_id]
→ 这个关节的位置状态在 qpos 中的起始下标

joint id
→ model.jnt_dofadr[joint_id]
→ 这个关节的速度状态在 qvel 中的起始下标
```

因此 joint id、`qpos` 下标和 `qvel` 下标描述的是不同对象，不能互相代替。

随后给 12 个驱动关节分别配置力矩执行器。例如某个关节名为：

```text
FL_hip_joint
```

对应执行器可以写成：

```xml
<actuator>
    <motor name="FL_hip_motor" joint="FL_hip_joint" gear="1"/>
    ...
</actuator>
```

12 个驱动关节都配置完成后：

```python
print(model.nu)
print(data.ctrl)
```

应看到 12 个控制输入。`data.ctrl[i]` 保存第 `i` 个 actuator 的标量控制输入；这个 actuator 通过 MJCF 中的 `joint="..."` 属性决定自己驱动哪个关节。`qpos` 的下标则来自该关节的状态布局，所以不能因为两个数组都能用 `i` 下标，就默认 `ctrl[i]` 对应 `qpos[i]`。

仓库提供了一个结构检查器。把机器人放进最终场景后可以直接运行：

```bash
python3 checks/check_quadruped_model.py scenes/flat_scene.xml
```

它会机械检查：

- MJCF 能否加载；
- 是否恰好有一个自由基座；
- 是否有 12 个执行器输入；
- 12 个执行器是否直接驱动 12 个不同关节；
- 初始状态和短时间零输入仿真是否保持有限数值；
- 初始 `ctrl` 是否全为 0。

## 构造平地场景和趴卧初始姿态

机器人本体和环境可以分开保存：

```text
models/robot.xml
scenes/flat_scene.xml
```

场景文件可以通过 `include` 引入机器人：

```xml
<mujoco model="flat_scene">
    <include file="../models/robot.xml"/>

    <worldbody>
        <geom name="floor" type="plane" size="5 5 0.1"/>
    </worldbody>
</mujoco>
```

先确认它能直接打开：

```bash
python3 -m mujoco.viewer --mjcf=scenes/flat_scene.xml
```

接下来要确定一组合理的初始状态。这里有两个问题：基座放多高，以及 12 个腿部关节分别取什么角度。

### 基座高度

如果转换后的自由关节没有名字，可以给它一个明确名称：

```xml
<freejoint name="base_freejoint"/>
```

然后通过已经学过的名字查询方式找到它：

```python
base_joint_id = mujoco.mj_name2id(
    model,
    mujoco.mjtObj.mjOBJ_JOINT,
    "base_freejoint",
)
base_qpos_adr = model.jnt_qposadr[base_joint_id]
```

自由关节在 `qpos` 中的前 3 个数是基座位置，因此：

```python
data.qpos[base_qpos_adr + 2] = 0.25
```

修改的是基座 z 坐标。具体数值由机器人尺寸决定；它只需要让初始机身处于合理高度，避免明显悬空或一开始就穿进地面。

### 先确认一个关节的正负方向

选一个实际腿部关节，例如：

```text
FL_hip_joint
```

查询它在 `qpos` 数组中的起始下标：

```python
joint_id = mujoco.mj_name2id(
    model,
    mujoco.mjtObj.mjOBJ_JOINT,
    "FL_hip_joint",
)
qpos_adr = model.jnt_qposadr[joint_id]
```

只修改这一项：

```python
data.qpos[qpos_adr] = 0.3
mujoco.mj_forward(model, data)
```

在可视化窗口中确认这个关节的机械位置和正负方向。hip、thigh、calf 都应该先有这种实际对应，之后再整理整组姿态。

当 12 个关节方向已经确认，可以把初始角放进一个字典：

```python
initial_joint_positions = {
    "FL_hip_joint": ...,
    "FL_thigh_joint": ...,
    "FL_calf_joint": ...,
    # 其余关节
}
```

再按名字逐个写入：

```python
for name, position in initial_joint_positions.items():
    joint_id = mujoco.mj_name2id(
        model,
        mujoco.mjtObj.mjOBJ_JOINT,
        name,
    )
    qpos_adr = model.jnt_qposadr[joint_id]
    data.qpos[qpos_adr] = position

mujoco.mj_forward(model, data)
```

这一步之后，先停在初始状态看模型。人工检查只保留机器很难可靠判断的机械现象：四条腿是否朝正确方向折叠、机身是否明显穿地、左右是否摆反、关节是否处于不合理极限位置。

## 零力矩运行与验收

任务要求所有关节输出力矩为 0：

```python
data.ctrl[:] = 0.0
```

然后进入仿真循环：

```python
mujoco.mj_step(model, data)
viewer.sync()
```

零力矩并不表示机器人完全没有受力。重力、地面接触、关节阻尼和摩擦仍然存在，因此模型可能先发生少量沉降和调整。

提交前先运行结构检查：

```bash
python3 checks/check_quadruped_model.py scenes/flat_scene.xml
```

全部通过后，再运行自己的初始化与仿真程序。最后的现场验收主要看机器难以替代的部分：

- 初始趴卧姿态是否符合实际机器人结构；
- 四条腿是否存在明显错向或左右颠倒；
- 是否持续穿地、滑动、抖动或弹飞；
- 是否有某个关节长期顶在角度范围边界。

如果程序需要额外的数值证据，可以周期性打印：

```python
print(data.qvel)
```

持续稳定以后，速度不应无限增大，也不应出现 `nan` 或 `inf`。

完成这一任务后，提交物应至少包含：机器人 MJCF、平地场景、初始化与仿真代码，以及能在本机重新运行的说明。模型结构的确定性条件由检查器给出明确结果；机械姿态和接触表现留给可视化窗口做最后确认。
