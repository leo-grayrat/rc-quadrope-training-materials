# 机器狗任务实现

仓库已经给出了这次要处理的真实机器人模型：

```text
第二次培训/black/
├── black_description.urdf
└── meshes/
    ├── trunk.STL
    ├── FL_hip.STL
    ├── FL_thigh.STL
    ├── FL_calf.STL
    └── ...
```

前面一直在 single joint 上建立 `joint → qpos/qvel → actuator → ctrl` 的关系。现在不换一套讲法，直接在这份真实 URDF 里追同一个关系。

## 沿着 `FL_hip_joint` 读进真实 URDF

在 `black_description.urdf` 中搜索：

```text
FL_hip_joint
```

会找到：

```xml
<joint name="FL_hip_joint" type="revolute">
    <parent link="trunk" />
    <child link="FL_hip" />
    <origin xyz="0.1566 0.060001 -0.06425" rpy="0 0 0" />
    <axis xyz="1 0 0" />
    <limit lower="-0.5" upper="0.5" effort="20" velocity="25" />
</joint>
```

这一个 joint 已经把前左腿的第一段机械关系写出来了：

```text
trunk
  ↓ FL_hip_joint
FL_hip
```

`parent` 和 `child` 指定它连接的两个 link；`origin` 给出这个关节相对父 link 的安装位置和姿态；`axis="1 0 0"` 表示它绕自己的 X 轴转动；`lower=-0.5`、`upper=0.5` 给出允许的角度范围，单位是 rad。

继续搜索 `FL_hip` 这个 child link，可以看到同一个刚体还带有显示、碰撞和惯量：

```xml
<link name="FL_hip">
    <visual>
        <geometry>
            <mesh filename="meshes/FL_hip.STL" />
        </geometry>
    </visual>

    <collision>
        <geometry>
            <cylinder radius="0.052" length="0.11" />
        </geometry>
    </collision>

    <inertial>
        <mass value="0.60559" />
        ...
    </inertial>
</link>
```

这里三类数据服务不同事情：

- `visual` 决定画面里看到的外形；
- `collision` 决定接触计算使用的几何；
- `inertial` 提供质量、质心和惯量。

`mesh filename="meshes/FL_hip.STL"` 还说明了一件很实际的事：这份机器人模型不只有一个 URDF 文件。URDF 通过相对路径引用了 `meshes/` 里的资源，所以只拿走 `black_description.urdf`，`FL_hip` 的显示网格就失去了来源。

沿着 child link 继续往下找，前左腿完整的机械链是：

```text
trunk
  ↓ FL_hip_joint
FL_hip
  ↓ FL_thigh_joint
FL_thigh
  ↓ FL_calf_joint
FL_calf
  ↓ FL_foot_fixed
FL_foot
```

前三个是 `revolute`，也就是这条腿真正需要控制的 3 个转动关节；`FL_foot_fixed` 把脚固定在小腿末端。四条腿各有 hip / thigh / calf，因此一共得到 12 个驱动关节。

## 把整套 URDF 资源交给 URDF Studio

培训任务指定使用 [URDF Studio](https://urdf.enkeebot.com/zh/) 把 URDF 转成 MJCF。

因为 `black_description.urdf` 会引用 `meshes/FL_hip.STL`、`meshes/trunk.STL` 等文件，网页端应拿到整个 `black/` 目录，而不是只有 XML：

```text
文件
→ 导入文件夹
→ 选择 black/
```

如果手里是打包好的 ZIP，也可以从“文件 → 导入文件”选择压缩包。导入成功后，网页三维视图应能显示机身和四条腿；某一段直接缺失时，再回到对应的 `mesh filename` 和实际文件路径查原因。

导出入口同样在顶部“文件”菜单：

```text
文件
→ 导出
→ MJCF
```

这里有两个选项和本任务直接相关。

### 为什么要开启“浮动基座”

原始 URDF 中有：

```xml
<joint name="floating_base" type="fixed">
    <parent link="base" />
    <child link="trunk" />
    ...
</joint>
```

这里的 `fixed` 表示 URDF 自己没有给机身一个可自由运动的根关节。但放到 MuJoCo 平地场景以后，整台机器狗需要能够在重力和接触作用下平移、转动，所以导出 MJCF 时开启 **“浮动基座”**。

URDF Studio 当前这个选项会在根 body 上加入 `<freejoint/>`。前面已经学过 free joint：它给 `qpos` 增加 7 个位置/姿态元素，给 `qvel` 增加 6 个速度元素。

### 为什么要关闭“包含执行器”

URDF Studio 的 MJCF 导出默认会生成执行器，而且默认执行器类型是位置控制。第二次任务明确要求关节驱动器使用**力矩模式**，后面还要自己把 12 个关节接到 `<motor>` actuator 上。

因此这里把 **“包含执行器”关闭**。转换先负责机器人本体，力矩执行器由我们自己加。

其它导出项保持：

- “在 ZIP 中包含网格文件”：开启；
- Mesh 目录：`meshes/`；
- 网格格式：自动；
- 质量设置：保持自动模式，保留 URDF 已经给出的质量和惯量。

点击 **“导出 ZIP”** 后，得到 MJCF XML 和它引用的 mesh 资源。解压时保持 XML 和 `meshes/` 的相对目录关系。

## 在 MuJoCo 里把 `FL_hip_joint` 找回来

把导出的 XML 放到自己的模型目录后，先直接加载：

```bash
python3 -m mujoco.viewer --mjcf=models/robot.xml
```

如果 XML 或 mesh 路径有问题，MuJoCo 会在这里直接报错。模型能加载以后，再回到已经学过的 Python API：

```python
import mujoco

model = mujoco.MjModel.from_xml_path("models/robot.xml")
data = mujoco.MjData(model)

print("njnt =", model.njnt)
print("nq =", model.nq)
print("nv =", model.nv)
```

这份 URDF 有 12 个 `revolute` 驱动关节。开启浮动基座以后，MuJoCo 中还会有 1 个 free joint。于是状态长度应能解释成：

```text
1 个 free joint
→ qpos 7
→ qvel 6

12 个 hinge joint
→ qpos 12
→ qvel 12
```

因此应得到：

```text
nq = 19
nv = 18
```

固定连接不会额外占 `qpos` / `qvel` 状态。

再把模型中的 joint 名全部打印出来：

```python
for joint_id in range(model.njnt):
    name = mujoco.mj_id2name(
        model,
        mujoco.mjtObj.mjOBJ_JOINT,
        joint_id,
    )
    print(
        joint_id,
        name,
        model.jnt_qposadr[joint_id],
        model.jnt_dofadr[joint_id],
    )
```

这里应该重新看到 `FL_hip_joint`、`FL_thigh_joint`、`FL_calf_joint`，以及另外三条腿的对应关节。

例如继续追 `FL_hip_joint`：

```python
joint_id = mujoco.mj_name2id(
    model,
    mujoco.mjtObj.mjOBJ_JOINT,
    "FL_hip_joint",
)

qpos_adr = model.jnt_qposadr[joint_id]
qvel_adr = model.jnt_dofadr[joint_id]

print(data.qpos[qpos_adr])
print(data.qvel[qvel_adr])
```

这就是 2.4 中 single joint 的同一条读取链，只是现在它真的落在完整四足模型上。

## 给真实的 12 个关节接上 `motor`

原始 URDF 中的 12 个驱动关节是：

```text
FL_hip_joint      FR_hip_joint      RL_hip_joint      RR_hip_joint
FL_thigh_joint    FR_thigh_joint    RL_thigh_joint    RR_thigh_joint
FL_calf_joint     FR_calf_joint     RL_calf_joint     RR_calf_joint
```

在 MJCF 的 `<actuator>` 中给每个关节增加一个 `motor`。例如前左腿：

```xml
<actuator>
    <motor name="FL_hip_motor"   joint="FL_hip_joint"   gear="1"/>
    <motor name="FL_thigh_motor" joint="FL_thigh_joint" gear="1"/>
    <motor name="FL_calf_motor"  joint="FL_calf_joint"  gear="1"/>

    <!-- 其余三条腿同样按各自 joint 名连接 -->
</actuator>
```

这里真正决定控制关系的是：

```text
motor 的 joint="FL_hip_joint"
        ↓
这个 actuator 驱动 FL_hip_joint
```

12 个 motor 都加完以后：

```python
print(model.nu)
print(data.ctrl)
```

应看到 12 个标量控制输入：

```text
model.nu = 12
```

`data.ctrl[i]` 的 `i` 是 actuator id，不是 `qpos` 下标。要知道某个 motor 实际写 `ctrl` 的哪一项，仍然按 actuator 名查询 id。

## 左右腿为什么不能直接填同一组有符号角度

真实 URDF 已经给了一个很有用的线索。比较两侧小腿：

```xml
<!-- 左前腿 -->
<joint name="FL_calf_joint" type="revolute">
    ...
    <limit lower="-2.5" upper="-0.85" ... />
</joint>

<!-- 右前腿 -->
<joint name="FR_calf_joint" type="revolute">
    ...
    <limit lower="0.85" upper="2.5" ... />
</joint>
```

两边完成相似的机械弯曲时，关节坐标的符号并不相同。左右镜像安装已经体现在 URDF 的 `origin`、关节方向和 range 中。

所以趴卧姿态不能写成“所有 calf 都设成同一个数”。程序应按关节名保存各自目标角：

```python
initial_joint_positions = {
    "FL_hip_joint": ...,
    "FL_thigh_joint": ...,
    "FL_calf_joint": ...,
    "FR_hip_joint": ...,
    "FR_thigh_joint": ...,
    "FR_calf_joint": ...,
    # RL / RR
}
```

对一个关节写入初始角仍然是 2.4 的做法：

```python
joint_id = mujoco.mj_name2id(
    model,
    mujoco.mjtObj.mjOBJ_JOINT,
    "FL_calf_joint",
)
qpos_adr = model.jnt_qposadr[joint_id]
data.qpos[qpos_adr] = initial_joint_positions["FL_calf_joint"]
```

写完一组 `qpos` 后调用：

```python
mujoco.mj_forward(model, data)
```

让 MuJoCo 根据新的位置状态更新整机几何，再在 Viewer 里看腿是否按 URDF 的机械方向折叠。

题目没有给一组唯一的趴卧关节角，所以这里真正需要自己确定的是这 12 个数；但每个数至少必须满足对应 joint 的 range，并且左右腿的符号要和真实模型的关节定义一致。

## 把机器人放到平地上

机器人本体可以保存在：

```text
models/robot.xml
```

场景另外写成：

```text
scenes/flat_scene.xml
```

例如：

```xml
<mujoco model="flat_scene">
    <include file="../models/robot.xml"/>

    <worldbody>
        <geom
            name="floor"
            type="plane"
            size="5 5 0.1"
        />
    </worldbody>
</mujoco>
```

free joint 的 `qpos` 前 3 个元素是机身位置。根据 free joint 名找到它的状态起点以后，可以修改 z 坐标：

```python
base_joint_id = ...
base_qpos_adr = model.jnt_qposadr[base_joint_id]

data.qpos[base_qpos_adr + 2] = ...
```

这里的高度和上面的 12 个关节角一起决定初始机械姿态：太低会直接穿进地面，太高则会在零力矩开始后明显下落。

## 零力矩运行

第二次任务要求关节输出力矩为 0：

```python
data.ctrl[:] = 0.0
```

仿真循环仍然是：

```python
while viewer.is_running():
    mujoco.mj_step(model, data)
    viewer.sync()
```

零力矩只说明 actuator 没有主动输出力矩。重力、碰撞、摩擦和关节自身的模型参数仍然会参与动力学，所以机器人可以发生沉降和接触调整。

仓库中的检查器可以验证模型结构和基本数值条件：

```bash
python3 checks/check_quadruped_model.py scenes/flat_scene.xml
```

它会检查：

- MJCF 是否能加载；
- 是否恰好有一个 free joint；
- `model.nu` 是否为 12；
- 12 个 actuator 是否分别驱动 12 个不同 joint；
- 初始 `ctrl` 是否全为 0；
- 零输入推进 200 步后 `qpos`、`qvel` 是否仍为有限数值。

这些结构条件通过以后，Viewer 里还要看机器人是否真的以合理的趴卧姿态落在平地上，以及四条腿有没有明显反向、穿地或处于关节极限。
