# 从 MuJoCo joint 到真实关节电机

第二次培训已经接触了 `qpos`、`qvel`、`ctrl`、motor actuator 和基本控制循环。第三次培训会突然出现转子、减速器、编码器、零位、`Kp`、`Kd`、前馈力矩和电机 SDK。它们其实都属于同一条关节驱动链。

这一节把这条链先搭起来。默认已经学过大学物理中的角速度、力矩、功率等概念，不重新讲基础力学；重点是看清这些物理量在机械结构和代码中分别位于哪里。

## 1. 先看完整的一条关节驱动链

对一个电机关节，可以先画成：

```text
上层控制程序
    │
    │ 期望关节状态 q_des, dq_des
    ▼
关节控制律
    │
    │ 期望关节力矩 tau_joint
    ▼
关节侧 / 转子侧换算
    │
    │ p_des, w_des, tau_motor, Kp_motor, Kd_motor
    ▼
电机驱动器
    │
    ▼
电机转子
    │
    │ 减速器
    ▼
减速器输出端
    │
    ▼
机器人关节 q
```

反馈方向则反过来：

```text
机器人关节
    ↑
减速器输出端
    ↑
电机转子
    │
    ▼
编码器
    │
    │ 转子位置读数
    ▼
减速比、零位等软件换算
    │
    ▼
上层使用的关节角 q、关节速度 dq
```

第三次培训的大部分术语都可以放进这两条路径中。

### 这几个机械名词分别在哪里

- **关节 / 输出端**：真正带动机器人腿部连杆转动的一侧。上层控制通常更关心这一侧的角度、速度和力矩。
- **电机转子**：电机内部高速旋转的一侧。
- **减速器**：连接转子和输出端。转子转得快、力矩小；输出端转得慢、力矩大。
- **编码器**：测量电机位置。第三次视频讨论的是转子侧单圈绝对值编码器。
- **电机驱动器与 SDK**：程序通过它发送位置、速度、增益、前馈力矩等命令，也从它读取反馈。

有了这张图以后，看到一个量时先问：**它是关节侧的，还是转子侧的？它在命令方向，还是反馈方向？**

## 2. 第二次培训的 MuJoCo 模型把很多层压扁了

第二次培训在最简单的 hinge joint 上使用：

```xml
<actuator>
    <motor joint="joint1" gear="1"/>
</actuator>
```

随后代码直接读取：

```python
q = data.qpos[qpos_adr]
dq = data.qvel[dof_adr]
```

再把控制输入写入：

```python
data.ctrl[actuator_id] = tau
```

在当前这种一对一 hinge、`gear="1"` 的简化模型里，可以直接把它理解成：

```text
qpos  → 关节角 q
qvel  → 关节角速度 dq
ctrl  → 施加到这个关节的驱动力矩 tau
```

因此第二次培训中的控制循环实际上已经留下了第三次培训的位置：

```text
读取 q / dq
    ↓
根据 q / dq 计算 tau
    ↓
写入 ctrl
    ↓
mj_step()
```

第二次主要学习了循环两端。第三次首先要补的是中间“怎样根据状态算力矩”。

真实电机比这个简化模型多出转子、减速器、编码器和电机驱动器，所以同样的 `q / dq / tau` 在进入硬件以前还要经过几层换算。

## 3. 从关节状态到关节力矩：第三次公式放在代码哪里

用

- $q$：当前关节角；
- $\dot q$：当前关节角速度；
- $q_{des}$：目标关节角；
- $\dot q_{des}$：目标关节角速度；
- $\tau_{ff}$：前馈力矩。

第三次视频使用的控制式可以写成：

$$
\tau_{joint}
=
\tau_{ff}
+K_p(q_{des}-q)
+K_d(\dot q_{des}-\dot q).
$$

从力学上看，关节受到合力矩以后产生角加速度。最简单的单自由度形式可以写成：

$$
I\ddot q = \sum \tau.
$$

因此这条控制式产生的并不是“目标角度本身”，而是当前这一时刻希望施加的力矩。

位置项

$$
K_p(q_{des}-q)
$$

根据位置误差产生回复力矩；速度项

$$
K_d(\dot q_{des}-\dot q)
$$

根据速度误差产生力矩。若 $\dot q_{des}=0$，速度项就是

$$
-K_d\dot q,
$$

与当前运动方向相反，表现出阻尼作用。$\tau_{ff}$ 则直接叠加一个力矩。

这正好填进已有 MuJoCo 循环：

```python
q = data.qpos[qpos_adr]
dq = data.qvel[dof_adr]

tau = (
    tau_ff
    + kp * (q_des - q)
    + kd * (dq_des - dq)
)

data.ctrl[actuator_id] = tau
mujoco.mj_step(model, data)
```

第三次视频里所说的位置模式、速度模式、阻尼模式、力矩模式和混合控制，可以看成对这几个命令量取不同值。代码骨架并没有换掉。

## 4. 真实关节多了一层减速器：同一个系统有两套角度

接下来把真实电机接进来。

记：

- $q$、$\dot q$、$\tau_j$：减速器输出端，也就是关节侧的角度、角速度和力矩；
- $p$、$\omega$、$\tau_m$：电机转子侧的角度、角速度和力矩；
- $N$：减速比，定义为转子转速与输出端转速之比。

先忽略安装方向的正负号。理想减速器有：

$$
p=Nq,
$$

$$
\omega=N\dot q.
$$

也就是说，输出端转一圈，转子需要转 $N$ 圈。

理想情况下忽略损耗，输入输出功率近似相同：

$$
\tau_m\omega=\tau_j\dot q.
$$

代入 $\omega=N\dot q$：

$$
\tau_j=N\tau_m.
$$

于是从关节侧目标换成转子侧命令时：

| 关节侧 | 转子侧 |
|---|---|
| 目标位置 $q_{des}$ | $p_{des}=Nq_{des}$ |
| 目标速度 $\dot q_{des}$ | $\omega_{des}=N\dot q_{des}$ |
| 目标力矩 $\tau_j$ | $\tau_m=\tau_j/N$ |

第三次视频里突然出现的“位置乘减速比、速度乘减速比、力矩除减速比”，来源就在这里。

本节把这层换算放在控制程序与电机接口之间理解；第二次培训里 `gear="1"` 的简化模型继续保持原来的含义。

## 5. 为什么增益还会出现 $N^2$

如果上层希望在关节侧使用：

$$
\tau_j
=
K_{p,j}(q_{des}-q)
+K_{d,j}(\dot q_{des}-\dot q),
$$

而电机驱动器内部使用转子侧位置和速度：

$$
\tau_m
=
K_{p,m}(p_{des}-p)
+K_{d,m}(\omega_{des}-\omega),
$$

已有：

$$
p_{des}-p=N(q_{des}-q)
$$

以及：

$$
\tau_j=N\tau_m.
$$

只看位置项：

$$
\tau_j
=N K_{p,m}(p_{des}-p)
=N K_{p,m}N(q_{des}-q).
$$

要让它和关节侧的 $K_{p,j}(q_{des}-q)$ 一致，需要：

$$
K_{p,m}=\frac{K_{p,j}}{N^2}.
$$

速度项同理：

$$
K_{d,m}=\frac{K_{d,j}}{N^2}.
$$

所以 $N^2$ 来自两次换算：一次是位置或速度误差从关节侧变到转子侧，另一次是电机力矩经过减速器变成关节力矩。

## 6. 编码器测到的是谁的角度

第三次视频接着讨论编码器。沿着前面的机械链看，问题很直接：编码器装在转子侧时，它首先给出的就是转子位置 $p$，而控制程序真正关心的通常是关节角 $q$。

若先忽略零位问题：

$$
q=\frac{p}{N}.
$$

实际装配以后，编码器自己的零点和机器人希望定义的关节零点通常不重合，因此软件还要做一次坐标变换。

可以定义：

$$
q=\frac{p}{N}+\mathrm{offset}.
$$

反过来，从关节目标得到转子目标：

$$
p_{cmd}=N(q_{des}-\mathrm{offset}).
$$

这里的 `offset` 可以直接理解成：**把编码器坐标系换成机器人关节坐标系所需要的零点偏移。**

不同资料可能把 `offset` 的正负方向定义得相反；只要先写清定义，反馈变换和命令变换应互为逆操作。

在代码中，这一层可以很明确：

```python
def rotor_to_joint_position(p, ratio, offset):
    return p / ratio + offset


def joint_to_rotor_position(q, ratio, offset):
    return ratio * (q - offset)
```

上层控制器仍然只需要面对 `q` 和 `q_des`。

## 7. 单圈绝对值编码器为什么会产生“候选零点”

如果编码器掉电重启后只能恢复当前一圈内的位置，可以把它抽象成：

$$
p_{raw}=p\bmod 2\pi.
$$

只知道 $p_{raw}$ 时，真实转子位置可能是：

$$
p_{raw},\quad
p_{raw}+2\pi,\quad
p_{raw}+4\pi,\quad\ldots
$$

也就是：

$$
p=p_{raw}+2k\pi.
$$

映射到关节侧：

$$
q_k=\frac{p_{raw}+2k\pi}{N}+\mathrm{offset}.
$$

相邻两个候选关节位置之间相差：

$$
\Delta q=\frac{2\pi}{N}.
$$

这就是第三次视频里“同一个转子圈内读数为什么可能对应多个输出端位置”的数学来源。

例如转子真实转过 370°，单圈读数重启后可能只显示 10°。仅凭这个 10°，软件无法知道之前累计了多少整圈。机器狗每次开机姿态接近、机械范围有限等条件，可以继续帮助判断当前对应哪个候选关节位置；第三次视频后半段的零点跳变处理就在解决这个问题。

## 8. 在软件里最好长期保留“关节侧”和“电机侧”两个概念

到了实机，代码可以按两层来想。

上层控制只使用机器人关节语义：

```text
JointState
    q
    dq

JointCommand
    q_des
    dq_des
    kp
    kd
    tau_ff
```

控制律也只在关节侧工作：

```python
tau_joint = (
    tau_ff
    + kp * (q_des - q)
    + kd * (dq_des - dq)
)
```

电机接口层负责机械和传感器换算：

```text
反馈方向：
编码器 / SDK 原始量
        ↓
减速比 + 零位
        ↓
JointState(q, dq)

命令方向：
JointCommand / tau_joint
        ↓
减速比 + 零位
        ↓
电机转子侧命令
```

这样以后换电机型号、减速比或零位定义时，控制器仍然可以继续使用同一套关节变量。

在第二次的 MuJoCo 简化模型里，这两层基本重合：`qpos/qvel` 已经直接给出关节状态，算出的关节力矩也可以直接写进 `ctrl`。到了真实电机，第三次培训是在这两者之间重新展开此前被仿真模型压扁的机械和接口层。

第三次视频 1 主要补：

      ↓

      ↓

      ↓

第三次视频 2 主要补：

因此第三次里看到下面这些词时，可以直接把它们放回整条驱动链：

| 术语 | 所在位置 |
|---|---|
| `q`、`dq` | 机器人关节侧状态 |
| `Kp`、`Kd`、前馈力矩 | 关节控制律 / 电机混合控制命令 |
| 转子 | 减速器高速侧 |
| 输出端 | 减速器低速侧，也是机器人关节侧 |
| 减速比 | 两侧位置、速度、力矩的变换关系 |
| 编码器 | 反馈测量 |
| 单圈绝对值 | 编码器掉电后可恢复的信息范围 |
| `offset` | 编码器坐标与机器人关节坐标之间的零点变换 |
| SDK 命令 | 软件最终送到电机驱动器的命令表示 |

第三次培训接下来会把这些概念放进真实电机任务。先有这条机械—控制—代码链，再读具体型号、6.33 减速比、零点跳变和 SDK 字段时，每个细节都有明确的位置。
