# 工程组织与 unitree_mujoco

基础任务跑通以后，人工任务还要求继续阅读 `unitree_mujoco`，思考自己的代码结构和线程设计。这里的出发点应该是你刚刚完成的程序，而不是先套一个复杂工程模板。

## 从自己的单文件程序开始

当前的 `simulate.py` 大致已经包含：

```text
加载模型
设置初始状态
创建 Viewer
读取状态
写 ctrl
mj_step
显示
```

几十行时全部写在一个文件里并没有问题。

如果后面继续加入：

- 机器人 joint 名称和索引管理；
- 控制器；
- 传感器读取；
- 日志；
- 网络或串口通信；

一个文件才会逐渐变得难维护。

这时可以按照职责拆分，例如：

```text
mujoco_project/
├── models/
├── scenes/
├── robot.py
├── simulator.py
├── controller.py
└── main.py
```

一种常见分工是：

- `robot.py` 保存机器人 joint、actuator 名称和状态读取逻辑；
- `simulator.py` 持有 `MjModel`、`MjData`，负责 `mj_step()`；
- `controller.py` 根据状态计算控制输入；
- `main.py` 创建这些对象并启动程序。

这不是必须遵守的目录模板。拆分的判断标准是：同一类职责是否已经开始和其他逻辑混在一起。

## Python 多文件之间怎样连接

Python 文件本身可以作为模块导入。

例如 `robot.py`：

```python
def print_robot_name():
    print("quadruped")
```

在 `main.py` 中：

```python
import robot

robot.print_robot_name()
```

也可以：

```python
from robot import print_robot_name

print_robot_name()
```

因此把代码拆到不同文件以后，并不是“每个文件各自运行”，而是由入口程序 import 其他模块并组合起来。

### 练习：先只做结构重构

把已经跑通的单文件程序拆成至少两个文件，但不要改变任何仿真行为。

要求：

- `main.py` 仍然能启动同一场景；
- 机器人初始姿态不变；
- `ctrl` 仍然保持 0；
- 运行结果和拆分前一致。

这一步只验证“拆文件”本身，不同时引入新的控制算法或线程。

## 仿真频率和控制频率

MuJoCo 的物理步长由：

```xml
<option timestep="..."/>
```

决定。

例如：

```text
timestep = 0.001 s
```

对应 1000 Hz 物理更新。

但控制器不一定每个物理步都重新计算。如果控制器每 0.02 s 更新一次，就是 50 Hz。此时一次控制量可以保持 20 个物理步：

```text
计算一次控制量
      ↓
mj_step × 20
      ↓
重新计算控制量
```

所以阅读别人代码时，要分清：

- 哪个循环负责物理 stepping；
- 控制量多久更新一次；
- Viewer 多久刷新一次。

这三个频率可以不同。

## 什么时候线程才有意义

一个最简单的仿真完全可以单线程：

```text
读状态
↓
算控制
↓
写 ctrl
↓
mj_step
↓
显示
```

线程通常在某些工作具有不同周期，或者会阻塞时才有实际价值。

例如：

- 仿真希望稳定地高频推进；
- 控制器较低频更新；
- 网络接收可能等待数据；
- 串口读取可能阻塞；
- 日志写盘没有必要卡住每一个物理步。

这时把某些工作放到独立线程，可以避免它们直接卡住仿真循环。

但线程也带来新的问题：多个线程如果同时读写同一份 `MjData`，就要考虑同步和数据一致性。

一个比较容易管理的思路是：

```text
             状态副本
仿真线程 ----------------> 控制线程
   |                         |
   |                         | 新控制量
   <-------------------------+
   |
   +----> 日志 / 通信
```

让负责 `mj_step()` 的线程持有并修改主要仿真状态，其他线程使用状态副本、控制命令或队列交换数据，比所有线程直接修改同一个 `MjData` 更容易理解和排查。

## 怎样读 unitree_mujoco

打开完整开源项目以后，不要从第一个文件开始逐行读。

先找到启动路径：

```text
README
↓
运行命令
↓
程序入口
↓
模型在哪里加载
↓
MjModel / MjData 在哪里创建
↓
主循环在哪里
↓
谁写 data.ctrl
↓
谁调用 mj_step
↓
Viewer / 通信 / 日志在哪里
```

可以在仓库中直接搜索关键词：

```bash
grep -R "mj_step" -n .
grep -R "ctrl" -n .
grep -R "MjModel" -n .
grep -R "Thread\|thread" -n .
```

找到位置以后，再沿函数调用关系往上、往下阅读。

看到一个线程时，至少回答：

1. 它执行什么工作；
2. 为什么不能直接放进主循环；
3. 它多久执行一次；
4. 它读什么数据；
5. 它写什么数据；
6. 数据怎样和其他线程同步。

看到一个类或模块时，也先回答它在整个流程中的职责，再看内部每个函数。

## 这部分任务最后应该得到什么

阅读 `unitree_mujoco` 以后，不要求把它整个重写一遍。更有价值的是拿自己的程序逐项比较：

```text
自己的程序              开源项目
----------------------------------------
模型加载在哪里      ↔   ?
状态怎样读取        ↔   ?
控制量怎样写入      ↔   ?
mj_step 在哪里      ↔   ?
Viewer 怎样更新     ↔   ?
有没有独立通信线程  ↔   ?
配置放在哪里        ↔   ?
```

然后挑出一两项确实能改善自己程序的结构。

如果自己的程序只有几十行，没有阻塞 I/O，也没有不同频率的独立工作，就没有必要为了“用了线程”而强行增加线程。能说明为什么当前不需要，也是一种有效的结构判断。
