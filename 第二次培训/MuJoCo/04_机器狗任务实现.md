# 机器狗任务实现

前 3 部分已经介绍了 MJCF、`MjModel` / `MjData`、关节、执行器和仿真循环。这一部分把这些内容连到第二次培训任务上。

任务最终需要得到：

```text
URDF
  ↓
整理后的 MJCF
  ↓
平坦场景
  ↓
力矩执行器
  ↓
合理的初始趴卧姿态
  ↓
data.ctrl[:] = 0
  ↓
运行后稳定
```

这里不提供最终 MJCF、关节名称和趴卧角度。它们取决于实际机器人模型，也正是这次任务需要自己处理的部分。

## 1. 先整理工作目录

可以先建立：

```text
quadruped_sim/
├── models/
│   ├── robot.xml
│   └── meshes/
├── scenes/
│   └── flat_scene.xml
├── model_info.py
└── simulate.py
```

仓库中的 [starter/04_quadruped](./starter/04_quadruped/) 已经提供 `model_info.py` 和 `simulate.py` 骨架。

其中：

- `models/robot.xml` 放自己从 URDF 转换并整理后的机器人；
- `models/meshes/` 保留模型引用的 STL / OBJ 等资源；
- `scenes/flat_scene.xml` 放平地和灯光；
- `model_info.py` 用来查看模型中的关节和执行器；
- `simulate.py` 设置初始状态并运行仿真。

## 2. URDF 转换以后先只检查模型

先不要写控制器。

转换得到 MJCF 后，第一步是确认它能被 MuJoCo 编译：

```bash
python3 -m mujoco.viewer --mjcf=models/robot.xml
```

也可以：

```bash
python3 model_info.py models/robot.xml
```

第二条命令会加载模型并列出：

```text
nq
nv
nu
njnt
nactuator
joint name
joint qpos address
joint dof address
actuator name
actuator target joint
```

如果此时就报错，先处理模型文件，不进入控制程序。

### mesh 找不到

例如：

```text
Error opening file ...
```

先从 `robot.xml` 所在目录检查实际路径：

```bash
find . -type f | sort
```

再查看：

```xml
<compiler meshdir="..."/>
```

和：

```xml
<mesh file="..."/>
```

中的路径。

移动 XML 时，mesh 的相对路径也会随之变化。

### 模型能打开以后

依次检查：

- 四条腿是否完整；
- 左右、前后腿有没有镜像错误；
- 关节轴方向是否符合模型；
- 关节 range 是否合理；
- base 是否有自由基座；
- 碰撞几何有没有明显错位；
- 机器人初始时有没有严重穿模。

这一步只检查模型，不处理“怎样趴下”。

## 3. 把机器人放进平坦场景

场景可以单独写。例如：

```xml
<mujoco model="flat_scene">
    <include file="../models/robot.xml"/>

    <worldbody>
        <light pos="0 0 3"/>

        <geom
            name="floor"
            type="plane"
            size="5 5 0.1"
            rgba="0.8 0.8 0.8 1"
        />
    </worldbody>
</mujoco>
```

`include` 的路径相对主 MJCF 文件所在目录解析。上面的场景位于 `scenes/`，因此使用 `../models/robot.xml`。

MuJoCo 会在解析阶段把 include 文件中的 XML 合并进主模型。机器人文件与场景文件如果都定义了 `compiler`、`option` 等全局设置，需要检查最终哪一组配置生效。初学阶段可以尽量把全局仿真选项集中在一个地方。

先单独打开场景：

```bash
python3 -m mujoco.viewer --mjcf=scenes/flat_scene.xml
```

确认地面和机器人能同时出现。

## 4. 给每个驱动关节加入 motor actuator

URDF 转换后的模型可能已经包含关节，但不一定包含任务要求的 actuator。

对于一个旋转关节：

```xml
<joint
    name="FL_hip_joint"
    type="hinge"
    axis="1 0 0"
/>
```

可以在 `actuator` 中加入：

```xml
<actuator>
    <motor
        name="FL_hip_motor"
        joint="FL_hip_joint"
        gear="1"
    />
</actuator>
```

任务要求使用力矩模式，因此这里使用 `motor` actuator。对于最简单的一对一 hinge joint，`motor` 是直接驱动执行器，`gear` 会影响输入与关节力矩之间的比例。

如果机器狗有 12 个独立驱动关节，通常需要为 12 个关节分别定义 actuator。

完成以后运行：

```bash
python3 model_info.py models/robot.xml
```

至少确认：

- `nactuator` 与预期驱动关节数量一致；
- 每个 actuator 指向正确的 joint；
- 没有漏掉某条腿；
- 没有把两个 actuator 错接到同一个 joint。

对于本任务使用的普通 `motor` actuator，控制输入写在 `data.ctrl` 中。

## 5. 不要直接猜 qpos 下标

原稿中给出了：

```python
joint_position = data.qpos[7:]
```

这种写法成立的前提是已经确认模型恰好只有一个自由基座，后面紧跟所有腿部关节。

自己整理模型时，可以先按名称定位关节：

```python
joint_id = mujoco.mj_name2id(
    model,
    mujoco.mjtObj.mjOBJ_JOINT,
    "FL_hip_joint",
)

qpos_adr = model.jnt_qposadr[joint_id]
data.qpos[qpos_adr] = 0.5
```

`mj_name2id()` 根据 XML 中的名称找到 joint id；`jnt_qposadr` 给出这个 joint 在 `qpos` 中的起始位置。

starter 中的 `set_hinge_joint()` 已经把这段查找逻辑写好：

```python
set_hinge_joint(
    model,
    data,
    "FL_hip_joint",
    0.5,
)
```

你需要填写的是**自己的关节名和初始角度**。

## 6. 设置自由基座高度

自由基座在 `qpos` 中占 7 个值：

```text
x y z qw qx qy qz
```

其中四元数 `(1, 0, 0, 0)` 表示没有额外旋转。

不要假设自由基座一定从 `qpos[0]` 开始。starter 会从模型中查找类型为 `free` 的 joint，再读取它的 `jnt_qposadr`。

本任务通常先只需要调整 base 的高度：

```python
INITIAL_BASE_HEIGHT = ...
```

高度过高时，机器人会先自由落体；高度过低时，机身或腿部可能和地面严重穿透。

## 7. 设置趴卧关节角

starter 中：

```python
INITIAL_JOINT_POSITIONS = {
    # "joint_name": angle_in_rad,
}
```

需要自己填写模型中的关节名称和角度。

例如结构上可能类似：

```python
INITIAL_JOINT_POSITIONS = {
    "FL_hip_joint": ...,
    "FL_thigh_joint": ...,
    "FL_calf_joint": ...,
    # ...
}
```

这里不提供具体数值。不同机器人的零位、关节轴、安装方向和 range 都可能不同。

确定初始角时可以同时看：

- URDF / MJCF 中的 joint axis；
- joint range；
- Viewer 中关节正方向；
- 机器人实际结构；
- 左右腿是否需要符号相反。

每次只调整少量关节，重新打开模型观察，比一次填完 12 个未知角度更容易定位错误。

## 8. 修改 qpos 后调用 mj_forward

手工修改：

```python
data.qpos[...]
```

以后，在正式 stepping 前调用：

```python
mujoco.mj_forward(model, data)
```

它会根据当前状态重新计算依赖的运动学和动力学量，但不推进仿真时间。

starter 已经把这一步放在初始姿态设置之后。

## 9. 保持零控制输入

任务要求关节输出力矩为 0。

starter 在进入循环前设置：

```python
data.ctrl[:] = 0.0
```

循环中也继续保持：

```python
if model.nu > 0:
    data.ctrl[:] = 0.0
```

这样即使后面继续修改程序，也能清楚看到当前任务没有额外控制器在写入非零输入。

这里不要加入 PD 控制来“把姿态锁住”。那会改变任务条件。

## 10. 怎样判断已经稳定

“画面看起来趴着”只能作为第一步观察。

可以同时查看：

```python
print(data.time)
print(data.qvel)
```

稳定以后，`qvel` 应逐渐接近较小范围，而不是持续保持明显速度。

还可以观察：

- base 是否持续下沉或漂移；
- 腿是否仍然缓慢滑动；
- 是否存在周期性抖动；
- 是否有明显穿透或突然弹起；
- 某个关节是否不断撞 limit。

如果零力矩下始终无法稳定，排查顺序可以是：

```text
初始 base 高度
    ↓
初始关节角
    ↓
碰撞几何
    ↓
质量 / 惯量
    ↓
关节 range / damping
    ↓
接触与摩擦参数
```

先确认模型和初始状态，再改仿真参数。

## 11. 推荐的实际操作顺序

可以按下面顺序完成任务：

1. 保存原始 URDF 和 mesh；
2. 完成 URDF → MJCF；
3. 单独用 Viewer 打开机器人 MJCF；
4. 用 `model_info.py` 查看 joint 与 actuator；
5. 修正 mesh、joint、freejoint 等模型问题；
6. 建立平坦场景；
7. 为所有驱动关节加入 motor actuator；
8. 再次用 `model_info.py` 核对 actuator；
9. 在 `simulate.py` 中填写 base 高度；
10. 逐步填写关节初始角；
11. 保持 `ctrl = 0` 运行；
12. 观察 `qvel`、接触和姿态；
13. 得到稳定趴卧状态后，再进入工程结构整理。

到第 12 步为止，对应人工任务中的基础 MuJoCo 仿真部分已经完成。之后再阅读 `unitree_mujoco`，比较它怎样组织模型、控制、线程和程序入口。
