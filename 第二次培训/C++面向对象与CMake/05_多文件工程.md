# 多文件工程

前面的代码都可以放在一个 `main.cpp` 中。类继续增加以后，一个文件会越来越难维护，因此 C++ 工程通常会把接口和实现拆到多个文件中。

## 声明与定义

例如头文件中写：

```cpp
class DMMotor : public Motor {
public:
    explicit DMMotor(int id);
    void enable() override;
};
```

这里给出了构造函数和 `enable()` 的函数签名，编译器由此知道这些函数存在以及怎样调用它们。这属于**声明**。

函数实现可以放在 `.cpp` 文件中：

```cpp
DMMotor::DMMotor(int id)
    : id_(id), position_(0.0)
{
}

void DMMotor::enable()
{
    ...
}
```

这部分属于**定义**。

常见的工程组织方式是：

- 头文件保存类定义、函数声明等需要被其他文件看到的内容；
- `.cpp` 文件保存函数实现。

有些短函数也会直接定义在头文件中，因此这条规则并非语法限制。当前练习先采用“头文件放接口，源文件放实现”的形式。

## 头文件、include 与 pragma once

如果 `dm_motor.hpp` 中使用了 `Motor`，需要包含对应头文件：

```cpp
#include "robot/motor.hpp"
```

预处理阶段会处理这条 `#include`，使当前编译单元能够看到 `Motor` 的定义。

同一个头文件可能通过多条 include 路径被重复包含。可以在头文件开头写：

```cpp
#pragma once
```

避免同一个头文件在一次编译中重复处理。传统的 include guard 也能达到相同目的。

## 每个 cpp 都会单独编译

假设目录中有：

```text
apps/main.cpp
src/dm_motor.cpp
src/unitree_motor.cpp
src/robot.cpp
```

编译器会分别处理这些 `.cpp` 文件。

可以手动生成目标文件：

```bash
g++ -c src/dm_motor.cpp -Iinclude -std=c++17 -o dm_motor.o
g++ -c src/unitree_motor.cpp -Iinclude -std=c++17 -o unitree_motor.o
g++ -c src/robot.cpp -Iinclude -std=c++17 -o robot.o
g++ -c apps/main.cpp -Iinclude -std=c++17 -o main.o
```

其中 `-c` 表示只编译，不进行最终链接。

随后把这些目标文件链接成一个可执行文件：

```bash
g++ main.o dm_motor.o unitree_motor.o robot.o -o robot_demo
```

也可以让 `g++` 在一次命令中完成编译和链接：

```bash
g++ apps/main.cpp \
    src/dm_motor.cpp \
    src/unitree_motor.cpp \
    src/robot.cpp \
    -Iinclude -std=c++17 -o robot_demo
```

`-Iinclude` 把 `include/` 加入头文件搜索路径，因此源码中可以写：

```cpp
#include "robot/motor.hpp"
```

## 编译错误与链接错误

下面这种语法错误会发生在编译阶段：

```cpp
left_motor_.enable(
```

当前 `.cpp` 无法被正确编译成目标文件。

另一种情况是，头文件中已经声明了函数：

```cpp
class DMMotor {
public:
    void enable();
};
```

使用这个函数的代码可以通过编译，但如果最终链接时没有包含提供 `DMMotor::enable()` 定义的目标文件，就可能出现：

```text
undefined reference to ...
```

这属于链接错误。

遇到构建失败时，先看错误发生在编译阶段还是链接阶段。两类问题的排查方向不同。

## namespace

工程中的类和函数通常放进命名空间：

```cpp
namespace robot {
    ...
}
```

使用时写：

```cpp
robot::DMMotor motor(1);
```

以后不同模块或第三方库都可能定义 `Motor`、`Controller`、`State` 等常见名称。命名空间可以避免这些名称全部进入全局作用域。
