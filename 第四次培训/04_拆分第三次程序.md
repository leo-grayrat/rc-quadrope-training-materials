# 把第三次程序真正拆开

前一篇已经跑通了 `JointState → controller_node → joint torque`。现在把第三次已有的 MuJoCo 程序接到另一端。

最终结构是：

```text
┌──────────────────────┐
│ controller_node C++  │
│ 状态机 / 轨迹 / PD   │
└──────────┬───────────┘
           │
   /joint_torques
           ↓
         ROS2
           ↑
    /joint_states
           │
┌──────────┴───────────┐
│ sim_node Python      │
│ MuJoCo / Viewer      │
│ data.qpos/qvel/ctrl  │
└──────────────────────┘
```

在第三次已有仿真程序外加入 ROS2 接口，发布关节状态并接收关节力矩。

## 1. 给第三次仿真程序包一层 ROS2 接口

创建 Python 包：

```bash
cd ~/ros2_ws/src
ros2 pkg create \
  --build-type ament_python \
  mujoco_bridge \
  --dependencies rclpy sensor_msgs std_msgs
```

这里的 `ament_python` 是 ROS2 Python 包的构建类型；`rclpy` 是 ROS2 的 Python 客户端库，对应上一节 C++ 使用的 `rclcpp`。

把第三次仿真程序放到：

```text
mujoco_bridge/mujoco_bridge/sim_node.py
```

加入 ROS2 依赖：

```python
import rclpy
from rclpy.node import Node
from sensor_msgs.msg import JointState
from std_msgs.msg import Float64MultiArray
```

建立桥接节点：

```python
class MujocoBridge(Node):
    def __init__(self):
        super().__init__('sim_node')

        self.state_pub = self.create_publisher(
            JointState, '/joint_states', 1)

        self.torque_sub = self.create_subscription(
            Float64MultiArray,
            '/joint_torques',
            self.torque_callback,
            1,
        )

        self.latest_tau = None

    def torque_callback(self, msg):
        self.latest_tau = list(msg.data)
```

状态发布继续使用第三次程序已有的 `joint_order` 和 `joints`：

```python
def publish_state(self, data, joint_order, joints):
    msg = JointState()
    msg.header.stamp = self.get_clock().now().to_msg()
    msg.name = list(joint_order)
    msg.position = [
        float(data.qpos[joints[name]['qpos_adr']])
        for name in joint_order
    ]
    msg.velocity = [
        float(data.qvel[joints[name]['qvel_adr']])
        for name in joint_order
    ]
    self.state_pub.publish(msg)
```

`msg.header.stamp` 是这条 `JointState` 消息的时间戳；`self.get_clock().now().to_msg()` 取得当前 ROS2 时钟时间并转换成消息字段需要的格式。发布出去的状态因此会携带“这份状态是什么时刻产生的”这一信息。

接收到的力矩再映射回 actuator：

```python
def apply_latest_torque(self, data, joint_order, joints):
    if self.latest_tau is None:
        return

    if len(self.latest_tau) != len(joint_order):
        return

    for name, tau in zip(joint_order, self.latest_tau):
        actuator_id = joints[name]['actuator_id']
        data.ctrl[actuator_id] = tau
```

仿真端采用 sample-and-hold：启动后还没收到力矩时沿用初始化控制量；收到一条完整力矩消息后，在下一条消息到来前继续使用最近一次结果。

此时两个方向已经对应起来：

```text
MuJoCo qpos/qvel
      ↓ joint_order
JointState
      ↓ /joint_states
controller_node
      ↓ /joint_torques
12 个 tau
      ↓ actuator_id
data.ctrl
```

## 2. 把 ROS2 处理放回原来的仿真循环

启动节点：

```python
rclpy.init()
node = MujocoBridge()
```

第三次原来的 Viewer 循环改成：

```python
while viewer.is_running():
    node.publish_state(data, joint_order, joints)

    rclpy.spin_once(node, timeout_sec=0.0)
    node.apply_latest_torque(data, joint_order, joints)

    mujoco.mj_step(model, data)
    viewer.sync()
```

退出时：

```python
node.destroy_node()
rclpy.shutdown()
```

`rclpy.spin_once(node, timeout_sec=0.0)` 处理当前已经就绪的一轮 ROS2 回调；`spin_once` 中的 `once` 表示这里只处理一次，而不是像 C++ 节点里的 `spin()` 那样持续占住执行流。`timeout_sec=0.0` 让这一调用不等待新消息，因此 MuJoCo 的仿真循环可以继续往下执行。

这样一轮仿真的执行顺序就是：

```text
发布当前关节状态
        ↓
处理已经到达的 ROS2 回调
        ↓
应用最近一次力矩
        ↓
mj_step
        ↓
viewer.sync
```

在 `mujoco_bridge/setup.py` 的 `console_scripts` 中注册：

```python
entry_points={
    'console_scripts': [
        'sim_node = mujoco_bridge.sim_node:main',
    ],
},
```

`console_scripts` 把命令名和 Python 入口函数对应起来：

```text
sim_node
→ mujoco_bridge.sim_node
→ main()
```

因此 `ros2 run mujoco_bridge sim_node` 最终会调用这个 `main()`。`sim_node.py` 的启动逻辑放进：

```python
def main(args=None):
    ...
```

原来的模型加载、`joints` 建立、Viewer 和仿真循环仍放在这个 `main()` 中。

再从第三个终端检查：

```bash
ros2 node list
ros2 topic list -t
ros2 topic info /joint_states
ros2 topic info /joint_torques
ros2 topic hz /joint_states
ros2 topic hz /joint_torques
```

应该看到：

```text
/controller_node
/sim_node
```

并且两条话题分别形成：

```text
/joint_states
  sim_node → controller_node

/joint_torques
  controller_node → sim_node
```

### 检查点

**产物**：`controller_node` 与 `sim_node` 两个独立程序，通过 ROS2 话题交换 12 关节状态和力矩。

**给定边界**：

- 复用第三次已有的 MuJoCo 模型加载、关节索引和仿真循环；
- 消息类型、话题名和 `joint_order` 沿用前一篇；
- `controller_node` 不直接读取 MuJoCo `data`；
- `sim_node` 不计算第三次的 PD、轨迹和状态机。

**判定方式**：

1. 两个包分别能构建并被 `ros2 run` 启动；
2. `ros2 node list` 同时出现两个节点；
3. `ros2 topic info` 显示两条话题都有正确的发布端和订阅端；
4. `ros2 topic echo /joint_states --once` 能看到 12 个关节名、位置和速度；
5. `ros2 topic echo /joint_torques --once` 能看到 12 个力矩；
6. 停掉 `controller_node` 后，`sim_node` 进程仍然运行。
