# 从第三次程序到两个节点

第三次的仿真控制可以抽成一条很清楚的数据流：

```text
q / dq
  ↓
状态机 + 目标轨迹 + PD
  ↓
tau
  ↓
MuJoCo data.ctrl
```

真实电机也有同样的上半段，只是在 `tau`、目标位置等控制量真正落到硬件之前，还要经过减速比、零位和 SDK。

第四次先不增加新的控制算法。我们只处理一个工程问题：**控制器为什么要和“谁来执行控制量”分开。**

## 1. 先把职责分开

把第三次程序按职责切开，可以得到两部分。

### 控制器

控制器只需要知道：

```text
当前关节状态 q / dq
        ↓
状态机、轨迹、PD
        ↓
关节控制量 tau
```

它不应该因为下面接的是 MuJoCo 还是实体电机，就重新写一套站立轨迹和 PD。

### 执行端

执行端负责把外部世界变成控制器认识的状态，并把控制器给出的命令真正执行：

```text
MuJoCo：
读取 qpos / qvel
        ↓
关节状态

关节力矩
        ↓
data.ctrl
```

```text
实机：
SDK + 编码器
        ↓
减速比 / offset
        ↓
关节状态

关节命令
        ↓
减速比 / offset
        ↓
SDK
```

这样切开以后，控制器面对的是一份**接口契约**，而不是某个具体后端。

## 2. “接口一样”具体意味着什么

“仿真和实机都能接收命令、反馈状态”只能说明我们有机会做统一接口。它并不自动保证控制器一行都不用改。

真正可替换，至少要求双方对下面这些量的含义达成一致：

| 项目 | 需要约定的内容 |
|---|---|
| 关节身份 | 有哪些关节，名字或顺序怎样对应 |
| 位置 | 单位是不是 rad，零位在哪里，正方向怎样定义 |
| 速度 | 单位是不是 rad/s，方向定义是否一致 |
| 控制量 | 发送的是关节侧力矩、目标位置，还是电机转子侧量 |
| 时间 | 状态多久更新一次，多久没有新命令算超时 |
| 边界 | 力矩、速度、位置的允许范围怎样处理 |

第三次已经解决了其中一部分：关节侧与电机侧怎样通过减速比和 offset 映射。第四次要做的是把这些约定变成程序之间真正交换的数据。

所以我们接下来先固定一个最小接口：

```text
执行端  -- joint state -->  控制器
执行端  <-- joint torque -- 控制器
```

控制器不直接读取 `data.qpos`，也不直接调用电机 SDK；执行端也不再自己计算 PD。

## 3. ROS2 在这里做什么

ROS2 提供了一套现成机制，让这些独立程序能够：

- 以**节点**的形式运行；
- 通过有名字、有类型的接口交换消息；
- 用命令行观察现在有哪些节点、哪些话题、消息在以什么频率流动；
- 在启动时统一传入参数，并由 launch 一次启动多个程序。

在这次培训里，可以先把结构理解成：

```text
controller_node
  订阅 joint_states
  发布 joint_torques
          ↕
      ROS2 graph
          ↕
sim_node / hardware_node
  发布 joint_states
  订阅 joint_torques
```

这里的“节点”是**运行时对象**。一个功能包可以保存多个源文件和可执行程序；某个可执行程序运行以后才会创建节点。ROS2 甚至允许一个进程里创建多个节点，只是本次为了让边界清楚，默认“一份可执行程序对应一个主要节点”。

这和“工作空间包含包、包又包含节点”的静态目录树不是一回事。

## 4. 先写接口表，再写 ROS2 代码

进入下一篇之前，先把自己第三次程序里的数据写成一张表。不要从 ROS2 API 开始倒推需求。

至少写清：

```text
状态：
- 关节名或固定顺序
- q 的单位和正方向
- dq 的单位和正方向

命令：
- 发送 tau 还是 q_des / dq_des / kp / kd / tau_ff
- 每个元素对应哪个关节
- 单位
```

本讲义后面采用一个简单版本：

- 状态用 `sensor_msgs/msg/JointState`；
- 控制器输出关节侧力矩，用 `std_msgs/msg/Float64MultiArray`；
- 状态里的 `name` 用来识别关节；
- 力矩数组按照第三次程序已有的 `joint_order` 排列，单位为 N·m。

`Float64MultiArray` 只是这次练习的过渡选择：它能让我们先练清楚节点边界和数据流。以后如果一条消息需要同时携带目标位置、目标速度、增益、前馈等不同语义，应定义更清楚的消息结构，而不是让一长串数组下标承担全部含义。
