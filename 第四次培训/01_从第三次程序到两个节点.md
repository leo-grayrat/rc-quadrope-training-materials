# 从第三次程序到两个节点

第三次的仿真控制可以抽成一条数据流：

```text
q / dq
  ↓
状态机 + 目标轨迹 + PD
  ↓
tau
  ↓
MuJoCo data.ctrl
```

第四次继续使用这套控制逻辑，只改变程序之间的组织方式：控制器负责根据关节状态计算控制量，执行端负责从 MuJoCo 读取状态并执行控制量。

## 1. 从一个程序拆成两种职责

### 控制器

```text
当前关节状态 q / dq
        ↓
状态机、轨迹、PD
        ↓
关节控制量 tau
```

控制器只处理关节侧状态和控制算法。

### 执行端

```text
MuJoCo qpos / qvel
        ↓
关节状态
        ↓
发送给控制器

控制器给出的关节力矩
        ↓
data.ctrl
```

于是第三次原来写在同一个循环里的关系变成：

```text
sim_node
  ── joint state ──→ controller_node
  ←─ joint torque ──
```

第三次的实体电机任务已经出现过减速比、offset、编码器和 SDK。它说明同一个“关节状态 / 关节命令”在落到不同执行端时会经过不同映射，也因此需要先把控制器看到的数据含义固定下来。

## 2. 先固定接口契约

程序分开以后，接口必须说明每个量到底代表什么。第四次使用下面这份最小约定：

| 项目 | 约定 |
|---|---|
| 关节身份 | 用关节名识别；输出数组按第三次已有的 `joint_order` 排列 |
| 位置 | 关节侧角度，rad |
| 速度 | 关节侧角速度，rad/s |
| 控制量 | 关节侧力矩，N·m |
| 状态消息 | `sensor_msgs/msg/JointState` |
| 力矩消息 | `std_msgs/msg/Float64MultiArray` |

数据流固定为：

```text
执行端  -- /joint_states -->  控制器
执行端  <-- /joint_torques -- 控制器
```

控制器不再读取 `data.qpos`，执行端也不再计算 PD。后面所有程序都沿用这份约定。

## 3. ROS2 把两边连起来

在本次程序里：

```text
controller_node
  订阅 /joint_states
  发布 /joint_torques
          ↕
        ROS2
          ↕
sim_node
  发布 /joint_states
  订阅 /joint_torques
```

ROS2 在这里提供三件马上会用到的能力：

- 把独立运行的程序组织成节点；
- 用有名字、有类型的话题交换数据；
- 用命令行观察节点、话题、消息和连接关系。

后面还会用参数保存启动配置，用 launch 一起启动两个节点。

“节点”属于运行时。一个功能包可以保存多个源文件和可执行程序；程序启动以后才会创建节点。下一篇先把一份最小 C++ 程序放进 ROS2 的构建和运行体系，再加入真正的状态与力矩话题。
