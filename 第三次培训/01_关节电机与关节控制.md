# 关节电机与关节控制

第二次培训已经把 MuJoCo 的基本控制链跑通：模型里有 joint 和 motor actuator，程序能从 `qpos`、`qvel` 读取状态，也能把控制量写进 `data.ctrl` 再调用 `mj_step()`。这一篇继续追一个前面一直留空的问题：**`ctrl` 里到底应该放什么，以及它和真实关节电机的控制有什么关系。**

第三次培训的视频先把关节电机近似成力矩源，再引出位置、速度、前馈和 PD 控制，最后又回到 MuJoCo 代码。沿这条线看，前后其实是同一个闭环：

```text
当前关节状态 q / dq
        ↓
根据目标计算力矩 tau
        ↓
电机 / actuator 施加力矩
        ↓
关节继续运动
        ↓
下一轮重新读取 q / dq
```

这一篇先只处理这一层。转子、减速器和编码器放到下一篇。

## 1. 从 `data.ctrl` 回到物理量

第二次培训中最简单的关节模型可以写成：

```xml
<actuator>
    <motor name="joint1_motor" joint="joint1" gear="1"/>
</actuator>
```

对于这种一对一的 hinge joint 和 `gear="1"`，这一阶段可以把程序中的三个量直接对应到关节侧：

```text
data.qpos[...]  → 关节角 q
data.qvel[...]  → 关节角速度 dq
data.ctrl[...]  → motor 的驱动输入，本任务中按关节力矩 tau 使用
```

于是此前的循环：

```python
q = data.qpos[qpos_adr]
dq = data.qvel[dof_adr]

# 这里计算控制输入

data.ctrl[actuator_id] = tau
mujoco.mj_step(model, data)
```

中间只差“怎样从当前状态得到 `tau`”。第三次视频第一段就在讲这件事。

## 2. 为什么可以先把关节电机看成力矩源

视频先给出一个工作近似：给电机一个设定力矩，实际输出力矩在正常工作范围内会接近这个值。这样上层控制程序暂时不需要展开电机内部的电流环、FOC 等细节，只关心“现在希望它输出多大的力矩”。

![](images/video1_02m00s_motor_curve.png)
*视频中的电机特性图：指令力矩与实际输出力矩，以及转速和力矩的关系*

图里也能看到这个近似有边界。小力矩时会受摩擦等因素影响，力矩过大时会碰到电流和输出能力限制；高转速下可用力矩也会下降。第三次当前要做的仿真只需要先把这一层压成“受控力矩源”，后面再讨论真实电机时补上传动和传感器。

从大学物理的角度，力矩作用在转动系统上会改变角速度。对最简单的单自由度模型可以写成：

$$
I\ddot q = \sum \tau.
$$

这里的控制器不会直接把“目标角度”塞给物理系统。它每一时刻根据当前角度、速度和目标值算出一个力矩，物理系统再在这个力矩作用下继续运动。

## 3. 五个命令量怎样得到一个力矩

视频使用的控制式为：

$$
\tau
=
\tau_{ff}
+K_p(p_{des}-p)
+K_d(\omega_{des}-\omega).
$$

![](images/video1_05m20s_pd_formula.png)
*视频中的五个命令量和力矩计算公式*

这一式里：

- $p$、$\omega$ 是当前角度和角速度；
- $p_{des}$、$\omega_{des}$ 是目标角度和目标角速度；
- $K_p$、$K_d$ 决定位置误差和速度误差产生多大的修正力矩；
- $\tau_{ff}$ 是直接叠加的前馈力矩。

视频这里使用的是电机接口里的符号 $p$、$\omega$。在 MuJoCo 的简化关节里，可以暂时把它们对应成关节侧的 $q$、$\dot q$。下一篇再区分真实电机中的转子侧和关节侧。

### 位置项

只保留位置项：

$$
\tau=K_p(p_{des}-p).
$$

如果当前位置低于目标位置，误差为正，控制器给出朝目标方向的力矩；越偏离目标，力矩越大。它在机械上很像一根把关节拉向目标位置的弹簧。

$K_p$ 决定这种“拉回去”的强弱。若角度使用 rad、力矩使用 N·m，那么 $K_p$ 的量纲可以理解为 N·m/rad。

### 速度项

只保留速度项：

$$
\tau=K_d(\omega_{des}-\omega).
$$

当目标速度取 0 时：

$$
\tau=-K_d\omega.
$$

关节朝正方向转，控制器给负力矩；朝负方向转，控制器给正力矩。这个项会抑制运动，因此表现为阻尼。

### 前馈力矩

若位置和速度反馈项都为零：

$$
\tau=\tau_{ff}.
$$

前馈项直接给出一个力矩。后面做更复杂的机器人控制时，它可以承担重力补偿、动力学模型输出等作用；本次只需要先知道它与两个反馈项并列相加。

## 4. PD 为什么会像“弹簧 + 阻尼器”

把位置项和速度项放在一起：

$$
\tau
=
K_p(p_{des}-p)
+K_d(\omega_{des}-\omega).
$$

若目标速度取 0：

$$
\tau
=
K_p(p_{des}-p)-K_d\omega.
$$

第一项始终把系统拉向目标位置，第二项抑制当前运动。对于一个简单转动系统，这就对应很直观的“弹簧 + 阻尼器”。

这也解释了为什么单独的位置反馈容易在目标附近来回振荡：当关节冲过目标位置时，位置项会反向把它拉回来，但系统本身已经有速度；速度项会在运动过程中消耗这部分运动趋势，使振荡更快衰减。

视频口头上有时会用“PID”泛指这一类控制，但画面上的公式没有积分项；这里按公式称为带前馈的 PD 控制。

## 5. 各种控制模式只是同一条公式的不同取值

视频随后列出力矩、零力矩、阻尼、速度、位置和混合控制等模式。

![](images/video1_12m10s_modes_table.png)
*视频中的控制模式表*

可以统一放回刚才的公式：

| 模式 | 主要保留的量 | 结果 |
|---|---|---|
| 力矩 | $\tau_{ff}$ | 直接给力矩 |
| 阻尼 | $K_d$，且 $\omega_{des}=0$ | $\tau=-K_d\omega$ |
| 速度 | $\omega_{des}$、$K_d$ | 根据速度误差产生力矩 |
| 位置 | $p_{des}$、$K_p$ | 根据位置误差产生力矩 |
| 混合控制 | 多个量同时保留 | 位置、速度和前馈共同作用 |

第三次仿真任务里的“阻尼模式”因此非常具体：每一轮读取各关节角速度，计算

$$
\tau=-K_d\dot q,
$$

再把结果写入对应 actuator。

## 6. 把公式接回 MuJoCo

视频后半段重新回到上一轮培训已经见过的 MJCF。想让程序自己算力矩，需要给驱动关节配置 `<motor>` actuator。

![](images/video1_15m10s_motor_config.png)
*视频中的 MuJoCo `<motor>` 执行器配置示例*

此时程序中的数据流已经完整：

```text
joint
  ↓
qpos / qvel
  ↓
当前 q / dq
  ↓
控制公式
  ↓
tau
  ↓
data.ctrl[actuator_id]
  ↓
mj_step()
```

代码的核心形式就是：

```python
q = data.qpos[qpos_adr]
dq = data.qvel[dof_adr]

tau = (
    tau_ff
    + kp * (q_des - q)
    + kd * (dq_des - dq)
)

tau = np.clip(tau, tau_min, tau_max)
data.ctrl[actuator_id] = tau
```

![](images/video1_16m35s_control_code.png)
*视频中的控制代码：读取状态、计算力矩、限幅并写入 `data.ctrl`*

`np.clip` 在这里表示力矩限幅。无论控制公式算出多大的值，真正写入 actuator 的力矩都限制在给定范围内。

这里还有一个容易混淆的下标问题。一个驱动关节至少会涉及：

```text
joint id
qpos 地址
qvel 地址
actuator id
```

它们来自模型中的不同编号体系。第二次已经学过如何从 joint 名找到 `qpos`、`qvel` 地址；第三次真正写控制器时，还需要建立 joint 与 actuator 的明确映射，再用 actuator id 写 `data.ctrl`。

## 7. 为什么这一阶段继续使用 `<motor>`

MuJoCo 还有 `<position>` 一类自带伺服行为的 actuator。视频特意要求本次继续使用 `<motor>`，然后在 Python 里自己读取状态并计算力矩。

这样做和第三次后面的实机内容衔接得很好：真实电机接口同样会出现当前位置、速度、目标位置、增益和前馈力矩。控制关系在程序里保持可见，进入实机以后只需要进一步处理转子、减速器、编码器和 SDK 的坐标关系。

## 8. 从一个关节扩展到四足机器人

单个关节的控制关系可以写成：

```text
(q, dq, q_des, dq_des, Kp, Kd, tau_ff)
                    ↓
                   tau
```

四足机器人只是同时对多个驱动关节做这件事。程序里真正需要组织的是每个关节对应的：

```text
关节名
qpos 地址
qvel 地址
actuator id
Kp / Kd
目标角
力矩限制
```

第三次任务要求的状态机随后会决定这些关节当前采用什么目标和什么控制方式：阻尼状态只需要速度反馈；站立状态则需要一组随时间变化的目标关节角，再由同一套 PD 公式算出力矩。

到这里，第二次培训中的 `qpos / qvel / ctrl` 已经和第三次的关节控制接上。下一篇开始展开真实关节里此前被 MuJoCo 简化掉的部分：**电机转子和机器人关节之间还隔着减速器，编码器测到的角度也不天然等于上层程序里的关节角。**
