# 关节电机与关节控制

第二次培训已经把 MuJoCo 的基本控制链跑通：模型里有 joint 和 motor actuator，程序能从 `qpos`、`qvel` 读取状态，也能把控制量写进 `data.ctrl` 再调用 `mj_step()`。

第三次从这里继续。前面真正空着的是中间这一段：

```text
当前关节状态 q / dq
        ↓
怎样得到控制量？
        ↓
data.ctrl
        ↓
mj_step()
```

关节电机、PD、阻尼和前馈都在回答这个问题。先把真实电机暂时看成“接受力矩命令并尽量输出相应力矩”的执行器，控制程序就可以围绕关节角、关节速度和力矩建立起来。转子、减速器和编码器留到下一篇再展开。

## 1. 从 `data.ctrl` 到关节电机的力矩

第二次培训中最简单的关节模型写成：

```xml
<actuator>
    <motor name="joint1_motor" joint="joint1" gear="1"/>
</actuator>
```

对于这种一对一 hinge joint 和 `gear="1"` 的模型，本次可以先按下面的关系理解：

```text
data.qpos[...]  → 当前关节角 q
data.qvel[...]  → 当前关节角速度 dq
data.ctrl[...]  → 这个 motor 的驱动输入，本任务按关节力矩 tau 使用
```

于是之前写过的循环：

```python
q = data.qpos[qpos_adr]
dq = data.qvel[dof_adr]

# 计算 tau

data.ctrl[actuator_id] = tau
mujoco.mj_step(model, data)
```

已经是一个控制器的骨架。第三次第一段视频就是从这里开始解释 `tau` 应该怎样算。

### 关节电机为什么可以先近似成力矩源

视频先给出一个工作近似：给电机设定一个力矩，实际输出在正常工作范围内会接近这个值。这样上层控制暂时可以忽略电流环、FOC 等内部实现，只关心“这一时刻希望关节受到多大的力矩”。

![](images/video1_02m00s_motor_curve.png)
*视频中的电机特性图：指令力矩与实际输出力矩，以及转速和力矩的关系*

图里也能看到这个近似的边界。小力矩会受到摩擦等因素影响，力矩过大时会碰到电流和输出能力限制，高转速下可用力矩也会下降。当前仿真任务先使用理想化的力矩控制关系，后面接真实电机时再处理传动和传感器。

从大学物理看，力矩改变转动状态。对最简单的单自由度模型可以写：

```math
I\ddot q = \sum \tau.
```

所以控制器每一轮做的事情很具体：读取当前角度和速度，算一个新的力矩；MuJoCo 再根据这个力矩推进下一时刻的角度和速度。`qpos / qvel / ctrl / mj_step` 至此和物理过程对上了。

## 2. 一个控制式怎样覆盖位置、速度、阻尼和前馈

视频使用的控制式是：

```math
\tau
=
\tau_{ff}
+K_p(p_{des}-p)
+K_d(\omega_{des}-\omega).
```

![](images/video1_05m20s_pd_formula.png)
*视频中的五个命令量和力矩计算公式*

这里的五个命令量分别是目标位置 $`p_{des}`$、目标角速度 $`\omega_{des}`$、位置增益 $`K_p`$、速度增益 $`K_d`$ 和前馈力矩 $`\tau_{ff}`$。电机还会读取当前位置 $`p`$ 和当前角速度 $`\omega`$。

视频使用的是电机接口里的符号 $`p`$、$`\omega`$。在当前 MuJoCo 简化关节里，可以暂时对应成关节侧的 $`q`$、$`\dot q`$。下一篇再把转子侧和输出端关节侧分开。

### 位置反馈：误差越大，拉回去的力矩越大

只保留位置项：

```math
\tau=K_p(p_{des}-p).
```

当前位置偏离目标越远，位置误差越大，回复力矩也越大。机械上可以把它理解成一根把关节拉向目标位置的弹簧。若角度单位是 rad、力矩单位是 N·m，那么 $`K_p`$ 可以理解为 N·m/rad。

这个控制只关心“离目标还有多远”。当关节已经带着速度冲向目标时，单独的位置项不会主动根据当前速度抑制运动，所以很容易在目标附近反复越过、拉回。

### 速度反馈：目标速度为零时就是阻尼

只保留速度项：

```math
\tau=K_d(\omega_{des}-\omega).
```

如果目标速度设为 0：

```math
\tau=-K_d\omega.
```

当前向正方向转，就得到负力矩；向负方向转，就得到正力矩。力矩始终压制当前运动，因此表现为阻尼。

这正好对应第三次任务里的阻尼状态：每个关节都不追某个固定位置，只根据当前角速度产生反向力矩。

### PD：把“拉向目标”和“抑制运动”放在一起

保留位置项和速度项：

```math
\tau
=
K_p(p_{des}-p)
+K_d(\omega_{des}-\omega).
```

若目标速度仍取 0：

```math
\tau
=
K_p(p_{des}-p)-K_d\omega.
```

位置项负责把关节拉向目标，速度项负责压制运动趋势。这就是视频里“弹簧 + 阻尼器”的直觉。视频口头上有时会用“PID”泛指这一类控制，但画面公式没有积分项，这里按公式称为带前馈的 PD 控制。

### 前馈：直接在反馈项之外加一个力矩

如果位置和速度反馈项都为零：

```math
\tau=\tau_{ff}.
```

前馈力矩直接进入最终命令。当前培训只需要先知道它和两个反馈项并列相加；以后更复杂的机器人控制可以把模型计算出的力矩放进这一项。

因此视频里的各种“模式”都能回到同一条式子：

![](images/video1_12m10s_modes_table.png)
*视频中的控制模式表*

| 模式 | 主要保留的量 | 控制效果 |
|---|---|---|
| 力矩 | $`\tau_{ff}`$ | 直接给力矩 |
| 阻尼 | $`K_d`$，且 $`\omega_{des}=0`$ | $`\tau=-K_d\omega`$ |
| 速度 | $`\omega_{des}`$、$`K_d`$ | 根据速度误差产生力矩 |
| 位置 | $`p_{des}`$、$`K_p`$ | 根据位置误差产生力矩 |
| 混合控制 | 多个量同时保留 | 位置、速度和前馈共同作用 |

不用把这些模式记成多套独立算法。真正要掌握的是同一条控制式里每一项的物理作用。

## 3. 把控制式放回 MuJoCo 程序

视频后半段重新回到上一轮已经见过的 MJCF。要让程序自己算力矩，需要给驱动关节配置 `<motor>` actuator。

![](images/video1_15m10s_motor_config.png)
*视频中的 MuJoCo `<motor>` 执行器配置示例*

这时数据流已经完整：

```text
joint
  ↓
qpos / qvel
  ↓
当前 q / dq
  ↓
PD / 前馈公式
  ↓
tau
  ↓
data.ctrl[actuator_id]
  ↓
mj_step()
```

代码核心可以写成：

```python
q = data.qpos[qpos_adr]
dq = data.qvel[dof_adr]

tau = (
    tau_ff
    + kp * (q_des - q)
    + kd * (dq_des - dq)
)

tau = max(tau_min, min(tau, tau_max))
data.ctrl[actuator_id] = tau
```

![](images/video1_16m35s_control_code.png)
*视频中的控制代码：读取状态、计算力矩、限幅并写入 `data.ctrl`*

这里最后一行之前做的是力矩限幅：若计算结果超出允许范围，就截到上下限。对单个标量力矩，用 Python 自带的 `min`、`max` 就够了，不需要额外引入数组库。

### joint、状态地址和 actuator id 是几套不同的编号

一个驱动关节至少会涉及：

```text
joint id
qpos 地址
qvel 地址
actuator id
```

第二次已经学过通过 joint 名查询 joint id：

```python
joint_id = mujoco.mj_name2id(
    model,
    mujoco.mjtObj.mjOBJ_JOINT,
    joint_name,
)
```

再从：

```python
model.jnt_qposadr[joint_id]
model.jnt_dofadr[joint_id]
```

得到 `qpos`、`qvel` 的地址。

actuator 也有自己的名字和 id。假设 MJCF 中写的是：

```xml
<motor name="joint1_motor" joint="joint1"/>
```

就可以按 actuator 类型查询：

```python
actuator_id = mujoco.mj_name2id(
    model,
    mujoco.mjtObj.mjOBJ_ACTUATOR,
    "joint1_motor",
)
```

这个 `actuator_id` 才是写 `data.ctrl[actuator_id]` 时使用的编号。

所以一条完整的对应关系是：

```text
joint_name
    ↓
joint id
    ├──→ qpos 地址 → data.qpos[...]
    └──→ qvel 地址 → data.qvel[...]

actuator_name
    ↓
actuator id
    ↓
data.ctrl[...]
```

控制程序需要知道某个 actuator 驱动的是哪个 joint，但不要因为模型里恰好只有一个关节，就把这些编号当成天然相同。

### 为什么本次继续使用 `<motor>`

MuJoCo 还提供 `<position>` 一类带伺服行为的 actuator。第三次视频要求继续使用 `<motor>`，由程序显式读取状态、计算力矩，再写 `ctrl`。

这样仿真和真实电机之间保留了同一条控制关系。下一篇进入真实关节时，控制式仍然存在，只是 `q / dq / tau` 在送进电机 SDK 前还要经过减速器和编码器的坐标换算。

选第二次培训里的 single joint，已经给定：

## 4. 从单关节控制扩展到四足机器人

单关节控制最终可以压缩成：

```text
(q, dq, q_des, dq_des, Kp, Kd, tau_ff)
                    ↓
                   tau
```

四足机器人没有改变这条关系，只是同一时刻要处理多个驱动关节。第二次已经使用过字典保存多关节信息，这里继续沿用相同方式即可。例如每个关节至少要关联：

```text
关节名
actuator 名
qpos 地址
qvel 地址
actuator id
Kp / Kd
目标角
力矩限制
```

第三次任务随后还会加状态机。阻尼状态下，每个关节主要使用速度反馈；站立状态下，程序要先生成一组随时间变化的目标关节角，再把这些目标交给同一套 PD 控制关系。

所以从第二次到这里，代码主线没有换：

```text
读取状态
    ↓
生成当前目标
    ↓
根据状态和目标算力矩
    ↓
写 ctrl
    ↓
推进仿真
```

下一篇才会展开真实关节中被 MuJoCo 简化掉的机械层：电机转子和机器人关节之间还有减速器，编码器测到的角度也要经过转换才能成为上层程序使用的关节角。
