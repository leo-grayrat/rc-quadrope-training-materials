# 第三次培训：任务与代码落点

这一篇只把原任务要求和前两段视频接到程序结构上。任务本身仍以 [第三次培训任务.pdf](./第三次培训任务.pdf) 为准。

## 1. 任务分成两条线

原任务有两部分。

### 仿真

在已有 MuJoCo 程序上加入关节电机控制，并写成至少包含两个状态的状态机：

- **阻尼模式**：所有关节处于阻尼状态；
- **站立模式**：按键后，从当前姿态连续过渡到站立姿态；另一个按键切回阻尼模式。

原任务文字里写了“差值，连续地站起来”。从程序行为看，关键要求是目标姿态不能瞬间跳到站立角，起立过程应连续变化。实现时可以把它写成随时间变化的目标角插值。

### 实体电机

原任务依次要求：

1. 先用宇树官方电机 SDK 例程让电机转起来；
2. 让电机缓慢回到 0 位置，再从键盘输入角度，让输出端缓慢转到指定角度；
3. 标记零点，把软件零点沿正方向偏移 30°，再次转到之前的目标角并观察；
4. 在前一步基础上处理视频里讲到的零点跳变。

因此，第三次最终要写的代码正好对应视频中的两条链：

```text
仿真：
q / dq
  ↓
状态机 + PD
  ↓
tau
  ↓
data.ctrl

实机：
关节目标
  ↓
减速比 + offset
  ↓
电机 SDK 命令
  ↓
电机
  ↓
编码器反馈
  ↓
减速比 + offset
  ↓
关节状态
```

## 2. 仿真部分：状态机控制的到底是什么

第二次的控制循环已经有：

```python
while viewer.is_running():
    # 读取状态
    # 计算控制输入
    # 写 ctrl
    mujoco.mj_step(model, data)
    viewer.sync()
```

第三次只需要把中间两步具体化。

### 阻尼模式

视频 1 给出的阻尼模式可以写成：

$$
\tau=-K_d\dot q.
$$

对多个关节，就是逐个读取关节速度，再得到对应力矩：

```python
for joint in joints:
    dq = ...
    tau = -kd * dq
    data.ctrl[joint.actuator_id] = tau
```

程序层面需要解决的是“哪个关节状态对应哪个 actuator”。第二次已经学过 joint id、`qpos` 地址和 `qvel` 地址；这里再补上 actuator id 的映射即可。

### 站立模式

站立状态仍然使用同一条 PD 控制式：

$$
\tau
=
K_p(q_{des}-q)
+K_d(\dot q_{des}-\dot q).
$$

变化的是 $q_{des}$。

如果按键瞬间把：

```text
q_des = 站立姿态
```

直接写进去，位置误差会突然变大，力矩也会突然变化。原任务要求“连续地站起来”，所以站立状态里还需要一个随时间推进的目标姿态。

设切换到站立时的关节角为 $q_0$，最终站立角为 $q_{stand}$，用进度 $s\in[0,1]$ 表示起立过程：

$$
q_{des}(s)=(1-s)q_0+s q_{stand}.
$$

代码结构可以是：

```python
if state == DAMPING:
    q_des = None
    # tau = -kd * dq

elif state == STANDING:
    s = ...  # 根据进入状态后的时间计算，并限制在 0~1
    q_des = (1 - s) * q_start + s * q_stand
    # 用 q_des、q、dq 算 PD 力矩
```

这里最重要的一点是：`q_start` 应在**切换到站立状态的那一刻**保存。这样从哪一个合理初始姿态进入站立，插值都从当时的真实关节角开始。

### 状态机只管理“当前应该采用哪套目标和控制律”

可以把主循环理解为：

```text
键盘输入
  ↓
决定当前 state
  ↓
state 生成 q_des / dq_des / 控制参数
  ↓
读取 q / dq
  ↓
计算 tau
  ↓
写 data.ctrl
  ↓
mj_step
```

这样状态机、PD 和 MuJoCo 三层职责不会混在一起。

## 3. 实机部分：代码里增加一层“电机坐标转换”

仿真中可以直接把关节角当作 `qpos`，真实电机里还要经过减速器和编码器。

推荐长期保留两套数据概念：

```text
JointState / JointCommand
    q, dq, q_des, dq_des, tau...

MotorState / MotorCommand
    rotor position, rotor velocity, motor torque...
```

两层之间由固定的转换函数连接。

### 反馈方向

如果编码器读到转子侧位置 $p$，减速比为 $N$，软件零位偏移定义为 `offset`：

$$
q=\frac{p}{N}+\mathrm{offset}.
$$

代码可以集中在一个函数里：

```python
def motor_to_joint_position(p, ratio, offset):
    return p / ratio + offset
```

### 命令方向

关节侧目标再反向换回转子侧：

$$
p_{cmd}=N(q_{des}-\mathrm{offset}).
$$

```python
def joint_to_motor_position(q_des, ratio, offset):
    return ratio * (q_des - offset)
```

如果实际 SDK 使用相反的 `offset` 符号定义，只需让这两个函数保持互为逆变换。上层控制器仍然使用统一的关节角。

## 4. “回到 0 位置”在程序里是什么

第 2 个实机任务要求让电机缓慢回到 0，再接受键盘输入角度。

程序可以分成：

```text
读取当前关节角 q_now
       ↓
生成连续目标 q_des(t)
       ↓
换算成电机侧目标
       ↓
通过 SDK 下发
```

“缓慢”对应的仍然是目标角随时间连续变化。它和仿真起立其实是同一种程序结构，只是底层输出从 `data.ctrl` 换成了电机 SDK。

因此可以把“生成连续目标”的逻辑单独写出来，仿真和实机都复用同一思路。

## 5. 软件零位偏移到底改了什么

视频 2 里标定和 `offset` 容易绕，是因为机械位置没变，程序使用的角度坐标变了。

假设某个机械位置原来在软件里读作：

```text
30°
```

现在希望把新的软件零点放到旧坐标的 50° 处，那么同一个机械位置在新坐标里应读作：

```text
30° - 50° = -20°
```

这一过程没有让电机移动，只改了“这个机械位置在程序里叫什么角度”。

所以实机程序里最好把零位处理限定在电机接口层：

```text
SDK 原始位置
    ↓
减速比
    ↓
offset
    ↓
统一的关节角 q
```

上层 PD、状态机和站立姿态都继续使用统一关节坐标。

## 6. 零点跳变：先理解成单圈信息丢失

单圈编码器重启后只保留当前圈内的位置：

$$
p_{raw}=p\bmod 2\pi.
$$

所以 10°、370°、730° 在重启后的单圈读数里都可能表现成 10°。

经过减速器后，不同的整圈数会对应不同的关节位置。视频里 10° 与 350° 的例子，就是靠近一圈边界时出现的回绕现象。

程序处理这件事时，需要分清两层：

```text
原始单圈读数有没有跨边界
        ↓
如果跨了，当前应选择哪个候选转子圈数
        ↓
再换算成关节角
```

可以先把“检测圈内读数跨边界”和“维护累计圈数 / 零位修正”写成独立函数，再把结果交给上层控制。这样不会把编码器细节塞进 PD 或状态机里。

## 7. 一套比较清楚的程序分层

做到第三次以后，程序可以逐渐形成下面的结构：

```text
输入 / 状态切换
      ↓
Behavior / State Machine
阻尼、站立、目标角生成
      ↓
Joint Controller
q, dq, q_des, dq_des → tau_joint
      ↓
Motor Interface
减速比、offset、编码器回绕、SDK 字段
      ↓
MuJoCo 或真实电机
```

仿真和实机的上半部分可以尽量保持相同：

```text
状态机
  ↓
关节目标
  ↓
关节控制
```

差异主要集中在最下面：

```text
仿真：tau_joint → data.ctrl → mj_step
实机：JointCommand → 电机侧换算 → SDK
```

这也是第二次培训里“工程组织”开始有实际意义的地方：拆文件时可以按真实职责拆，而不用先追求抽象的“结构是否优秀”。

## 8. 做任务时可以按这条顺序推进

1. 先把现有 12 个关节与 actuator 映射整理清楚；
2. 只实现阻尼状态，确认每个关节的速度反馈和输出力矩方向正确；
3. 加站立状态，先保存切换瞬间的 `q_start`，再生成连续 `q_des`；
4. 把状态机和 PD 控制从 MuJoCo 主循环中分开；
5. 实机先跑通 SDK 的单电机读写，再把反馈和命令统一换成关节侧坐标；
6. 在统一关节坐标下完成“回 0”和键盘目标；
7. 最后加入 `offset` 与单圈跳变处理。

做到这里，第三次视频里的机械细节、控制公式和程序结构就会落在同一条数据链上。
