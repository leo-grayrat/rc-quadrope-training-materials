# 第三次任务实现

前两篇已经把第三次需要的两条基础链路搭起来：

```text
仿真关节：
q / dq
  ↓
PD / 阻尼 / 前馈
  ↓
tau
  ↓
data.ctrl

真实关节：
关节侧 q / dq / tau
  ↕ 减速比、零位、编码器
转子侧 p / omega / tau_motor
  ↕
电机 SDK
```

第三次任务要把这些内容组织成程序。仿真部分要求阻尼和站立两个状态；实体电机部分要求先跑通 SDK，再完成缓慢回零、键盘目标、软件零位偏移和零点跳变处理。

原始要求以 [第三次培训任务.pdf](./第三次培训任务.pdf) 为准。这一篇重点放在程序怎么连接这些已经学过的量，以及哪些部分应该由你自己完成。

## 1. 仿真：从阻尼状态到连续站立

第二次培训中的机器狗程序已经能加载模型、设置初始 `qpos`、创建 Viewer、写 `ctrl` 并不断调用 `mj_step()`。第三次加入控制后，主循环开始真正形成闭环：

```text
键盘输入 / 当前状态
        ↓
状态机决定当前模式
        ↓
读取各关节 q / dq
        ↓
生成这一轮的目标
        ↓
根据目标和状态计算 tau
        ↓
力矩限幅
        ↓
写入对应 data.ctrl
        ↓
mj_step()
```

### 先把 joint 和 actuator 对应关系整理清楚

控制 12 个驱动关节时，程序不能继续依赖 `qpos[7]`、`ctrl[3]` 这类固定数字。每个关节至少需要知道：

```text
joint name
qpos address
qvel address
actuator id
```

第二次已经学过根据 joint 名查询 joint id，再通过：

```python
model.jnt_qposadr[joint_id]
model.jnt_dofadr[joint_id]
```

得到状态地址。第三次只需要把 actuator id 一起整理进同一份数据结构。例如：

```python
class JointInfo:
    def __init__(self, name, qpos_adr, qvel_adr, actuator_id):
        self.name = name
        self.qpos_adr = qpos_adr
        self.qvel_adr = qvel_adr
        self.actuator_id = actuator_id
```

这里的数据结构形式可以自己调整，关键是让控制循环能从“这个关节”明确走到它的状态和 actuator。

### 阻尼状态

阻尼模式已经在第一篇得到：

$$
\tau=-K_d\dot q.
$$

所以这一状态没有目标位置。每个关节只需要读取当前 `dq`，得到反向力矩，再限幅并写给对应 actuator：

```text
qvel
  ↓
dq
  ↓
-Kd * dq
  ↓
clip
  ↓
data.ctrl
```

这也是很好的第一步检查：如果某个关节正在向一个方向转，阻尼力矩应该压制这个运动。若结果相反，优先检查速度符号、关节安装方向和 actuator 映射。

### 站立状态的核心是目标角随时间变化

站立仍然可以使用同一条 PD：

$$
\tau
=
K_p(q_{des}-q)
+K_d(\dot q_{des}-\dot q).
$$

任务要求机器狗从当前姿态连续地站起来，因此 `q_des` 不能在按键瞬间直接从当前值跳到最终站立角。一个直接的实现方式是：进入站立状态时先记录当前实际姿态 $q_0$，之后逐渐把目标从 $q_0$ 移到 $q_{stand}$。

用 $s\in[0,1]$ 表示起立进度：

$$
q_{des}(s)=(1-s)q_0+s q_{stand}.
$$

切换瞬间需要保存：

```python
q_start = current_joint_positions.copy()
stand_start_time = data.time
```

后面的每一轮根据已经过去的时间计算 $s$，再得到当前 `q_des`。这样目标从真实的切换姿态开始，不依赖一个写死的初始姿势。

状态机和控制器的职责可以分开理解：

```text
State Machine / Target Generator
DAMPING  → 不给位置目标，使用阻尼规则
STANDING → 生成 q_des(t)
        ↓
Joint Controller
q / dq / q_des / dq_des → tau
        ↓
MuJoCo
ctrl → mj_step
```

状态机决定“现在采用什么目标和规则”，PD 负责“给定当前状态和目标以后算出多大力矩”。

### 练习 1：补完一个有边界的状态机

给自己写一个最小版本，只需要两个状态：

```python
DAMPING = 0
STANDING = 1
```

要求你自己完成：

1. 从当前 12 个关节状态构造 `q_current`、`dq_current`；
2. 进入 `STANDING` 的瞬间保存 `q_start` 和开始时间；
3. 计算 $s$，并限制在 $[0,1]$；
4. 生成 `q_des`；
5. 对每个关节算出 `tau` 并写到正确 actuator；
6. 切回 `DAMPING` 时恢复阻尼控制。

先不要加入更多状态，也不要先做复杂插值。完成后应该能说明：按键逻辑、目标生成、PD 和 MuJoCo 推进分别位于程序的哪一层。

## 2. 实机：把上层关节命令接到电机 SDK

原任务的实体部分先要求用宇树官方 SDK 例程把电机转起来。这一步最值得做的是把示例程序中的字段和前两篇的概念对应起来。

第一次读 SDK 示例时，重点追：

```text
当前转子位置 p
当前转子速度 omega
目标位置 p_des
目标速度 omega_des
Kp / Kd
tau_ff
```

然后确认这些量怎样进入电机命令、怎样从反馈结构里读回来。

上层程序最好继续使用机器人关节语义：

```text
JointState
q, dq

JointCommand
q_des, dq_des, kp, kd, tau_ff
```

Motor Interface 再把它换成电机侧：

```text
JointCommand
        ↓
减速比 + offset + 安装方向
        ↓
Motor Command
        ↓
Unitree SDK
```

反馈方向反过来：

```text
SDK feedback
        ↓
转子位置 / 速度
        ↓
编码器回绕 + 减速比 + offset
        ↓
JointState
```

### “缓慢回到 0”其实还是目标轨迹生成

实体任务第二步要求让电机缓慢回到 0，然后根据键盘输入的角度缓慢转到新目标。

这个结构和仿真里的连续站立高度相似：

```text
读取当前关节角 q_now
        ↓
记录为 q_start
        ↓
逐步生成 q_des(t)
        ↓
换算到电机侧
        ↓
SDK 下发
```

可以复用同样的线性插值思想：

```python
def interpolate_position(q_start, q_target, s):
    return (1 - s) * q_start + s * q_target
```

区别只在最下面：仿真最终把力矩写入 `data.ctrl`，实体程序最终生成电机 SDK 需要的命令。

### 键盘输入应该停留在关节侧

如果用户输入：

```text
30°
```

程序最好把它解释成“输出端关节相对软件零位的 30°”。随后接口层再负责：

```text
关节目标 30°
      ↓
offset
      ↓
减速比 N
      ↓
转子目标角
      ↓
SDK
```

这样上层状态机和交互代码都不需要记某个电机内部要转多少圈。

### 练习 2：把仿真中的目标生成复用到单电机

已经有一个函数：

```python
def interpolate_position(q_start, q_target, s):
    ...
```

再假设你已经能通过 SDK 得到转子侧 `p`，并能发送 `p_des`。

请自己补出中间这条链：

```text
p feedback
   ↓
转成当前关节角 q_now
   ↓
从 q_now 生成连续 q_des(t)
   ↓
转回 p_des
   ↓
SDK
```

先只处理位置、减速比和 `offset`，暂时不加入零点跳变。完成后确认：同一个 `q_des` 在修改 `ratio` 或 `offset` 后，SDK 侧的 `p_des` 会怎样变化。

## 3. 软件零位和重启后的单圈跳变

实体任务后两步开始真正使用第二篇的编码器内容。

任务先要求标记一个零位，然后把软件零位沿正方向偏移 30°。这一步改的是坐标关系。假设程序采用：

$$
q=\frac{p}{N}+offset,
$$

那么改变 `offset` 后，同一个机械位置会得到不同的 `q`；反向下发目标时：

$$
p_{cmd}=N(q_{des}-offset),
$$

同一个 `q_des` 也会对应新的机械位置。

所以零位处理适合集中在 Motor Interface，而不是散落到状态机和 PD 控制器中。

可以先单独检查两个函数是否互逆：

```python
def motor_to_joint_position(p, ratio, offset):
    ...


def joint_to_motor_position(q, ratio, offset):
    ...
```

任选若干 `p`，先转成 `q`，再转回 `p_back`。如果定义一致，`p_back` 应回到原值。

### 重启以后，先处理圈内回绕，再决定候选整圈

单圈编码器给出的原始读数可以抽象成：

$$
p_{raw}=p\bmod 2\pi.
$$

所以反馈处理至少要经过：

```text
SDK 单圈位置 p_raw
        ↓
判断圈内是否跨过 0 / 2pi 边界
        ↓
结合机械姿态或历史信息选择候选整圈 k
        ↓
得到连续转子位置 p
        ↓
减速比 + offset
        ↓
关节角 q
```

视频用 10° 和 350° 说明边界附近的情况。普通减法会把它们看成相差 340°，圆周上的最短变化却只有 20°。这说明“圈内回绕”应该先在电机反馈层处理，之后上层控制器再使用连续的关节状态。

PD 和状态机没有必要知道编码器为什么会从 10° 变成 350°。它们只应该拿到已经解释好的 `q`、`dq`。

机器人机械姿态看起来几乎没变。

然后再决定这些逻辑应该属于 `EncoderState`、`MotorInterface`、`JointController` 还是状态机中的哪一层。这里没有要求直接写出完整跳变识别算法，先把职责边界画清楚。

## 4. 第三次以后，程序结构开始有了真正的分层依据

做到这里，第二次培训里“考虑代码结构”的要求终于有了具体对象。程序可以逐渐形成：

```text
Keyboard / Behavior
按键、阻尼、站立、目标角
        ↓
Target Generator
连续目标 q_des(t)
        ↓
Joint Controller
q / dq / q_des / dq_des → tau 或 JointCommand
        ↓
Motor Interface
减速比、安装方向、offset、编码器回绕
        ↓
Simulation Backend        Hardware Backend
MuJoCo ctrl / mj_step     Unitree SDK
```

这些层来自实际数据职责：

- Behavior 决定机器人当前想做什么；
- Target Generator 生成连续目标；
- Joint Controller 根据关节状态和目标计算控制量；
- Motor Interface 负责关节侧和电机侧的机械、传感器转换；
- Backend 负责真正调用 MuJoCo 或硬件 SDK。

仿真和实机可以共享上半部分的关节语义。MuJoCo 把很多机械细节压在模型内部，所以仿真 backend 很薄；真实电机需要显式处理转子、减速器和编码器。

实际完成任务时，可以按依赖关系推进：先整理 joint/actuator 映射并跑通阻尼，再做站立目标生成；实机先读懂 SDK 的状态和命令字段，再建立 Motor Interface，完成回零和键盘目标，最后加入软件零位和单圈跳变处理。

到这里，第三次培训的机械细节、控制理论和代码结构已经落到同一套数据流中。后面的工作会越来越像真实机器人软件：上层始终以关节状态思考，底层负责把这些量可靠地送到仿真器或电机。
