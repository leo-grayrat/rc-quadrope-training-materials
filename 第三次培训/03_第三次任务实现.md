# 第三次任务实现

前两篇已经把第三次培训需要的两条基础链路建立起来：

```text
仿真关节：
q / dq
  ↓
PD / 阻尼 / 前馈
  ↓
tau
  ↓
data.ctrl

真实关节：
关节侧 q / dq / tau
  ↕ 减速比、零位、编码器
转子侧 p / omega / tau_motor
  ↕
电机 SDK
```

第三次任务要求把这些东西真正组织成程序。仿真部分要加入阻尼和站立状态；实体电机部分要完成 SDK 基本控制、缓慢回零、键盘目标、软件零位偏移和单圈零点跳变处理。

原始要求以 [第三次培训任务.pdf](./第三次培训任务.pdf) 为准。这一篇主要讲程序怎样拆、各部分数据怎样连接，以及哪些地方需要自己完成。

## 1. 仿真任务新增了什么

第二次培训中的机器狗程序已经能：

```text
加载模型
设置初始 qpos
创建 Viewer
写 ctrl
mj_step
```

第三次加入控制以后，主循环变成：

```text
读取键盘 / 当前状态
        ↓
状态机决定当前模式
        ↓
读取各关节 q / dq
        ↓
根据模式生成目标并计算 tau
        ↓
力矩限幅
        ↓
写入各 actuator 的 data.ctrl
        ↓
mj_step
        ↓
viewer.sync
```

状态机的职责只到“当前采用哪套目标和控制规则”。MuJoCo 仍然负责推进物理仿真。

## 2. 先整理好关节和 actuator 的映射

第三次的控制器会反复访问 12 个驱动关节。程序需要知道每个关节对应：

```text
joint name
qpos address
qvel address
actuator id
```

第二次已经学过从 joint 名查询 joint id，再通过：

```python
model.jnt_qposadr[joint_id]
model.jnt_dofadr[joint_id]
```

得到状态地址。

第三次再把 actuator 一起整理起来。可以用一个小的数据结构集中保存：

```python
class JointInfo:
    def __init__(self, name, qpos_adr, qvel_adr, actuator_id):
        self.name = name
        self.qpos_adr = qpos_adr
        self.qvel_adr = qvel_adr
        self.actuator_id = actuator_id
```

具体怎样从 actuator 名或模型结构找到 `actuator_id`，可以沿第二次“根据名字查对象”的思路完成。最终控制循环里不要再到处手写 `qpos[7]`、`ctrl[3]` 这种缺少语义的固定下标。

## 3. 阻尼模式

任务要求的第一个状态是阻尼模式。

上一篇已经得到：

$$
\tau=-K_d\dot q.
$$

所以每个关节在这一状态下只需要：

```text
读取 dq
  ↓
乘 -Kd
  ↓
限幅
  ↓
写入对应 actuator
```

代码骨架可以写成：

```python
def damping_torque(dq, kd):
    return -kd * dq
```

主循环中再对所有驱动关节调用它。

这里最值得检查的是方向和映射。如果某个关节旋转后阻尼力矩反而继续推动它，优先检查关节方向、速度符号和 actuator 对应关系。

## 4. 站立模式仍然使用同一个 PD

站立时可以继续使用：

$$
\tau
=
K_p(q_{des}-q)
+K_d(\dot q_{des}-\dot q).
$$

真正新增的问题是：**$q_{des}$ 不能在按键的一瞬间从当前值直接跳成最终站立角。**

任务要求机器狗连续地站起来，因此程序要生成一段随时间变化的目标姿态。

设切换到站立模式时的实际关节角为 $q_0$，最终站立姿态为 $q_{stand}$，用 $s\in[0,1]$ 表示起立进度。最简单的线性插值为：

$$
q_{des}(s)
=(1-s)q_0+s q_{stand}.
$$

其中：

```text
s = 0   → q_des = q0
s = 1   → q_des = q_stand
```

因此进入站立状态的那一刻，需要把当前所有关节角保存下来：

```python
q_start = current_joint_positions.copy()
stand_start_time = data.time
```

后面的每一轮再根据经过时间计算 $s$。

## 5. 为什么要保存切换瞬间的 `q_start`

如果程序永远从一个写死的初始姿态插值到站立姿态，那么机器狗稍微换了初始姿势，目标轨迹就会从一个并不存在的位置开始。

状态切换时记录当前关节角以后，程序得到的是：

```text
当前真实姿态 q_start
        ↓
连续目标 q_des(t)
        ↓
最终站立姿态 q_stand
```

这也让“从当前姿态连续站起来”真正落到代码里。

状态机可以保持很简单：

```python
if state == DAMPING:
    # tau = -kd * dq

elif state == STANDING:
    # 根据进入状态后的时间得到 s
    # q_des = interpolate(q_start, q_stand, s)
    # tau = PD(q, dq, q_des, dq_des)
```

按键只负责触发状态切换，不需要把控制计算写进键盘处理代码。

## 6. 目标生成、控制器、仿真器分开

到这里程序里已经有三类职责：

```text
State Machine / Target Generator
决定阻尼还是站立
生成 q_des(t)
        ↓
Joint Controller
q, dq, q_des, dq_des → tau
        ↓
MuJoCo
ctrl → mj_step
```

把它们分开以后，后面的实机程序可以复用上两层。换到真实电机时，状态机仍然产生关节目标，控制器仍然使用关节状态；变化主要集中在最下面的电机接口。

这一点也解释了第二次培训为什么开始要求考虑程序结构。现在已经有了真实职责，可以根据数据流拆模块，不需要抽象地追求“文件越多越工程化”。

## 7. 实体电机任务先从 SDK 的读写链开始

原任务的第一步要求使用宇树官方电机 SDK 例程让电机转起来。

第一次接触 SDK 时，重点追四类量：

```text
当前转子位置 p
当前转子速度 omega
发送的目标位置 / 目标速度
发送的 Kp / Kd / tau_ff
```

把示例程序中的这些字段和前两篇的公式对上以后，再开始写自己的封装。此时最重要的数据边界是：

```text
上层程序使用关节侧单位
        ↓
Motor Interface
减速比 / 安装方向 / offset / 编码器处理
        ↓
SDK 使用电机侧单位
```

后续任务都建立在这一层上。

## 8. 建立统一的关节侧接口

可以让上层程序只认识：

```python
class JointState:
    q = ...
    dq = ...


class JointCommand:
    q_des = ...
    dq_des = ...
    kp = ...
    kd = ...
    tau_ff = ...
```

电机接口层负责把 SDK 反馈转换成 `JointState`，再把 `JointCommand` 转成 SDK 命令。

位置换算沿用上一篇的一种约定：

$$
q=\frac{p}{N}+offset,
$$

$$
p_{cmd}=N(q_{des}-offset).
$$

速度和力矩则按减速比换算：

$$
\dot q=\frac{\omega}{N},
$$

$$
\tau_m=\frac{\tau_j}{N}.
$$

如果直接使用电机内部的混合位置控制，还要同时转换 $K_p$、$K_d$。

## 9. “缓慢回到 0”也是目标轨迹生成

实体电机任务要求先让电机缓慢回到 0 位置，再允许键盘输入一个角度，让输出端缓慢转到目标角。

程序结构和仿真的连续起立非常相似：

```text
读取当前关节角 q_now
        ↓
记录为 q_start
        ↓
从 q_start 连续生成到 q_target 的 q_des(t)
        ↓
转换成电机侧命令
        ↓
SDK 下发
```

所以可以把目标插值单独写成可复用函数：

```python
def interpolate_position(q_start, q_target, s):
    return (1 - s) * q_start + s * q_target
```

仿真里的“起立”和实机里的“缓慢回零 / 缓慢到目标角”都可以复用同一思路，只是最终输出接口不同。

## 10. 键盘输入的角度应当属于关节侧

如果上层用户输入：

```text
30°
```

程序最好把它解释成“机器人关节输出端相对软件零位的 30°”。

随后 Motor Interface 再做：

```text
30° 的关节目标
      ↓
考虑 offset
      ↓
乘减速比 N
      ↓
得到转子侧目标
      ↓
发送给 SDK
```

这样用户、状态机和控制器都不需要记住某个型号电机内部到底需要转多少圈。

## 11. 软件零位偏移 30°

任务后面要求标记零位，再把软件零位沿正方向偏移 30°，重新发送目标并观察实际位置。

这一操作应该只修改坐标变换参数。

假设使用：

$$
q=\frac{p}{N}+offset,
$$

修改 `offset` 后，同一个机械位置会得到不同的关节坐标；反向命令函数也会使用同一个新 `offset`，因此同一个 `q_des` 最终对应的机械位置会随零位移动。

这一步适合直接检查两个互逆函数：

```python
q = motor_to_joint_position(p, ratio, offset)
p_back = joint_to_motor_position(q, ratio, offset)
```

对于同一组参数，`p_back` 应回到原来的转子位置。先确认坐标变换本身，再接真实电机控制，可以减少符号方向混乱。

## 12. 单圈编码器的零点跳变应该留在接口层

上一篇已经得到：

$$
p_{raw}=p\bmod 2\pi.
$$

真实程序如果只拿 `p_raw` 直接除以减速比，一旦读数跨过 0 / $2\pi$ 边界，关节角就会突然跳变。

因此反馈处理至少有两步：

```text
SDK 单圈位置 p_raw
        ↓
根据连续性处理回绕 / 当前候选圈数
        ↓
连续转子位置 p
        ↓
减速比 + offset
        ↓
关节角 q
```

视频用 10° 和 350° 举例说明边界附近的情况。程序中可以把“单圈角是否跨边界”作为独立问题处理，得到连续的转子位置以后，再交给后续的减速比和零位换算。

这样 PD 控制器和状态机完全不需要知道编码器为什么会从 10° 变成 350°。

## 13. 第三次以后程序可以形成这样的分层

```text
Keyboard / Behavior
按键、阻尼、站立、目标角
        ↓
Target Generator
连续目标 q_des(t)
        ↓
Joint Controller
q / dq / q_des / dq_des → tau 或 JointCommand
        ↓
Motor Interface
减速比、安装方向、offset、编码器回绕
        ↓
Simulation Backend        Hardware Backend
MuJoCo ctrl / mj_step     Unitree SDK
```

仿真和实机可以共享上半部分的关节语义。MuJoCo 模型把很多机械细节直接压进模型里，所以仿真 backend 很薄；真实电机 backend 要显式处理转子、减速器和编码器。

## 14. 推荐的实现顺序

完成任务时可以按下面的依赖关系推进：

1. 整理 12 个 joint 与 actuator 的映射，让每个关节的 `q`、`dq` 和 `ctrl` 都能明确定位；
2. 完成仿真阻尼模式，确认速度方向和阻尼力矩方向；
3. 加入状态机，并在切换到站立时保存 `q_start`；
4. 生成连续的站立目标 `q_des(t)`，再用 PD 计算力矩；
5. 跑通实体电机 SDK 示例，认清位置、速度、增益和力矩字段；
6. 写 Motor Interface，把 SDK 的转子侧量统一换成关节侧量；
7. 在关节侧完成缓慢回零和键盘目标；
8. 加入软件零位参数；
9. 最后处理单圈读数回绕和零点跳变。

这条顺序的关键是始终保持同一套关节侧语义。机械换算和 SDK 细节集中在接口层以后，前两篇的理论关系、仿真代码和真实电机控制就会落在同一套程序结构里。
