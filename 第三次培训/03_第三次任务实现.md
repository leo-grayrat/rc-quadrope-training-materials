# 第三次任务实现

前两篇已经把第三次需要的两条基础链路搭起来：

```text
仿真关节：
q / dq
  ↓
PD / 阻尼 / 前馈
  ↓
tau
  ↓
data.ctrl

真实关节：
关节侧 q / dq / tau
  ↕ 减速比、零位、编码器
转子侧 p / omega / tau_motor
  ↕
电机 SDK
```

第三次任务要把这些内容组织成程序。仿真部分要求阻尼和站立两个状态；实体电机部分要求先跑通 SDK，再完成缓慢回零、键盘目标、软件零位偏移和零点跳变处理。

原始要求以 [第三次培训任务.pdf](./第三次培训任务.pdf) 为准。这一篇重点放在程序怎么连接这些已经学过的量，以及哪些部分应该由你自己完成。

## 1. 仿真：从阻尼状态到连续站立

第二次培训中的机器狗程序已经能加载模型、设置初始 `qpos`、创建 Viewer、写 `ctrl` 并不断调用 `mj_step()`。第三次加入控制后，主循环开始真正形成闭环：

```text
键盘输入 / 当前状态
        ↓
状态机决定当前模式
        ↓
读取各关节 q / dq
        ↓
生成这一轮的目标
        ↓
根据目标和状态计算 tau
        ↓
力矩限幅
        ↓
写入对应 data.ctrl
        ↓
mj_step()
```

### 先把 12 个 joint 和 actuator 对应起来

控制 12 个驱动关节时，程序不能继续依赖 `qpos[7]`、`ctrl[3]` 这类固定数字。每个关节至少需要知道：

```text
joint name
actuator name
qpos address
qvel address
actuator id
```

第一篇已经把这些查询关系补完整。这里可以继续使用第二次已经学过的字典，把每个关节的信息集中保存。例如：

```python
joints = {
    "FL_hip_joint": {
        "actuator_name": "FL_hip_motor",
        "qpos_adr": ...,
        "qvel_adr": ...,
        "actuator_id": ...,
    },
    # 其余关节
}
```

字典中的地址和 id 仍然要根据模型实际查询得到。这样后面的控制循环可以按关节名遍历，不需要额外引入一套 Python 类写法。

### Viewer 中的按键怎样进入状态机

MuJoCo 的 passive viewer 可以接收一个 `key_callback`。先用一个字典保存按键希望切换到的状态：

```python
DAMPING = 0
STANDING = 1

keyboard = {
    "requested_state": DAMPING,
}


def key_callback(keycode):
    key = chr(keycode).upper()

    if key == "D":
        keyboard["requested_state"] = DAMPING
    elif key == "S":
        keyboard["requested_state"] = STANDING
```

Viewer 传进来的 `keycode` 是按键编码，Python 的 `chr()` 把它转成单个字符；`.upper()` 让大小写按键都按同一个字母处理。

启动 Viewer 时把这个函数交进去：

```python
with mujoco.viewer.launch_passive(
    model,
    data,
    key_callback=key_callback,
) as viewer:
    ...
```

回调只负责修改 `keyboard["requested_state"]`。真正的状态切换、保存起始姿态和控制计算仍然放在仿真主循环里。这样按键处理不会和 PD 公式混在一起。

### 阻尼状态

阻尼模式已经在第一篇得到：

```math
\tau=-K_d\dot q.
```

所以这一状态没有目标位置。每个关节只需要读取当前 `dq`，得到反向力矩，再限幅并写给对应 actuator：

```text
qvel
  ↓
dq
  ↓
-Kd * dq
  ↓
limit
  ↓
data.ctrl
```

这是很直接的一步检查：如果某个关节正在向一个方向转，阻尼力矩应该压制这个运动。若结果相反，先检查速度符号和 joint / actuator 对应关系。

### 站立状态：目标位置和目标速度都要定义

站立继续使用：

```math
\tau
=
K_p(q_{des}-q)
+K_d(\dot q_{des}-\dot q).
```

任务要求机器狗从当前姿态连续站起来，因此 `q_des` 不能在按键瞬间直接跳到最终站立角。

设切换到站立状态时的实际关节角为 $`q_0`$，最终站立姿态为 $`q_{stand}`$，希望整个过程用时 $`T`$。进入状态后经过时间：

```math
t_{elapsed}=t-t_0.
```

先把它归一化为：

```math
s=\mathrm{clip}\left(\frac{t_{elapsed}}{T},0,1\right).
```

代码里对标量可以写：

```python
elapsed = data.time - stand_start_time
s = max(0.0, min(elapsed / stand_duration, 1.0))
```

目标位置做线性插值：

```math
q_{des}(s)=(1-s)q_0+s q_{stand}.
```

在线性运动阶段 $`0<s<1`$，它对应的目标速度是常数：

```math
\dot q_{des}=\frac{q_{stand}-q_0}{T}.
```

到达最终姿态后令：

```math
\dot q_{des}=0.
```

这样 PD 里的位置目标和速度目标都有明确来源。对每个关节分别使用自己的 $`q_0`$ 和 $`q_{stand}`$ 即可。

状态切换瞬间需要保存：

```python
q_start = {
    name: data.qpos[info["qpos_adr"]]
    for name, info in joints.items()
}
stand_start_time = data.time
```

最终站立角也可以用同样的字典形式保存：

```python
q_stand = {
    "FL_hip_joint": ...,
    # 其余关节
}
```

于是某一个关节当前的目标来自：

```text
q_start[name]
      ↓
线性插值
      ↓
q_des
      ↓
与 dq_des 一起进入 PD
```

这里不要求把 12 个关节强行组成 NumPy 向量；按字典逐关节计算已经足够完成任务。

### 状态切换时到底发生什么

主循环每轮查看 `keyboard["requested_state"]`。当它和当前状态不同，才执行一次进入新状态需要的初始化。

按下 `S` 后，需要保存 `q_start`、记录 `stand_start_time`，然后把当前状态改成 `STANDING`。之后每一轮只根据当前时间重新计算 `s`、`q_des`、`dq_des` 和力矩。按下 `D` 后则回到阻尼规则。

这样几类工作自然分开：

```text
按键
  ↓
选择状态
  ↓
生成本轮目标
  ↓
PD / 阻尼计算力矩
  ↓
MuJoCo 推进
```

### 练习 1：补完一个有边界的状态机

给自己写一个最小版本，只需要两个状态：

```python
DAMPING = 0
STANDING = 1
```

要求你自己完成：

1. 查询并整理 12 个 joint / actuator 的对应信息；
2. 接入 `key_callback`，用 `D`、`S` 请求切换状态；
3. 进入 `STANDING` 的瞬间保存 `q_start` 和开始时间；
4. 根据 `stand_duration` 计算 `s`；
5. 对每个关节生成 `q_des`、`dq_des`；
6. 按当前状态计算 `tau`，限幅后写到正确 actuator；
7. 切回 `DAMPING` 时恢复阻尼控制。

完成后应该能从一个具体关节出发，指出它的当前状态在哪里读、目标在哪里生成、力矩在哪里算、最终写到哪个 `ctrl`。

## 2. 实机：把关节目标接到电机 SDK

原任务的实体部分先要求用宇树官方 SDK 例程把电机转起来。第一次读 SDK 示例时，先把里面的字段和前两篇已经建立的量对应起来：

```text
当前转子位置 p
当前转子速度 omega
目标位置 p_des
目标速度 omega_des
Kp / Kd
tau_ff
```

确认这些量怎样进入电机命令、怎样从反馈结构里读回来以后，再写自己的换算函数。

上层程序继续使用机器人关节语义即可。这里的“关节状态”“关节命令”只是对一组量的称呼，可以继续用普通字典保存：

```python
joint_state = {
    "q": ...,
    "dq": ...,
}

joint_command = {
    "q_des": ...,
    "dq_des": ...,
    "kp": ...,
    "kd": ...,
    "tau_ff": ...,
}
```

靠近 SDK 的函数负责把它们转换成电机侧的位置、速度、增益和前馈力矩；反馈方向再把电机侧状态还原成 `q`、`dq`。

### “缓慢回到 0”仍然是目标轨迹生成

实体任务要求先让电机缓慢回到 0，再根据键盘输入的角度缓慢转到新目标。

这和仿真的连续站立使用同一种结构：

```text
读取当前关节角 q_now
        ↓
记录为 q_start
        ↓
根据持续时间 T 生成 q_des(t), dq_des(t)
        ↓
换算到电机侧
        ↓
SDK 下发
```

前面的线性插值公式可以直接复用。变化只发生在最下面：仿真最终自己计算 `tau` 并写 `data.ctrl`；若实体电机 SDK 接受位置、速度、增益和前馈，则需要先按第二篇的关系把这些关节侧量换成转子侧命令。

### 键盘输入角度时统一换成 rad

人输入角度时用“30°”更直观，但程序内部仍保持 rad。例如一次运动结束后，再等待用户输入下一个关节目标：

```python
import math

angle_deg = float(input("target angle (deg): "))
q_target = math.radians(angle_deg)
```

接下来所有插值和关节侧计算都使用 `q_target`。

这里的 `input()` 放在两次运动之间；真正执行一次从当前位置到目标位置的运动时，控制循环仍然连续运行。等这一段运动结束以后，再回到终端等待下一次输入即可。这样不会在电机正在执行连续控制时突然停住控制循环。

随后再按第二篇的关系：

```text
q_target
   ↓
offset
   ↓
减速比 N
   ↓
p_des
   ↓
SDK
```

### 练习 2：把仿真中的目标生成复用到单电机

假设你已经能通过 SDK 得到转子侧位置 `p`，也能发送转子侧目标 `p_des`。

请自己完成：

```text
p feedback
   ↓
换成当前关节角 q_now
   ↓
记录 q_start
   ↓
从 q_start 到 q_target 生成 q_des(t), dq_des(t)
```

## 3. 软件零位和单圈跳变怎样接进实机程序

任务后两步开始真正使用第二篇的编码器内容。

任务先要求标记一个零位，然后把软件零位沿正方向偏移 30°。假设程序采用：

```math
q=\frac{p}{N}+offset,
```

那么改变 `offset` 后，同一个机械位置会得到不同的 `q`；反向下发目标时：

```math
p_{cmd}=N(q_{des}-offset).
```

同一个 `q_des` 也会对应新的机械位置。

零位换算可以集中成两个互逆函数：

```python
def motor_to_joint_position(p, ratio, offset):
    ...


def joint_to_motor_position(q, ratio, offset):
    ...
```

先任选若干 `p`，转成 `q` 再转回 `p_back`。定义一致时，`p_back` 应回到原值。确认坐标换算以后，再接真实电机。

### 重启后怎样恢复连续位置

第二篇已经把单圈编码器的处理顺序讲清：

```text
原始圈内读数 p_raw
        ↓
根据前后读数判断是否跨过 0 / 2π 边界
        ↓
更新累计圈数 k
        ↓
p = p_raw + 2kπ
        ↓
减速比 + offset
        ↓
关节角 q
```

实现时保留上一时刻的 `prev_raw` 和当前累计圈数 `k`。若从低端跳到高端，例如 10°→350°，按照连续小运动理解为向负方向跨边界，`k` 减一；若从高端跳到低端，例如 350°→10°，则 `k` 加一。

刚上电时还没有连续历史可用，这时需要结合机器人的已知启动姿态，在多个候选圈数里选择一个合理的初始 `k`。得到初始候选以后，运行期间再靠前后读数维持连续性。

这些处理都放在电机反馈换算处。上面的 PD、目标生成和状态逻辑只使用已经还原好的 `q`、`dq`。

### 练习 3：把单电机反馈链补完整

给定：

```text
ratio = 已知减速比
offset = 已标定软件零位
prev_raw = 上一时刻单圈读数
curr_raw = 当前单圈读数
k = 当前累计圈数
```

自己完成一段反馈处理，使它能够：

1. 判断本次是否从单圈低端跨到高端，或从高端跨到低端；
2. 更新 `k`；
3. 计算连续转子位置 `p`；
4. 计算关节角 `q`；
5. 把新的 `curr_raw` 保存成下一轮的 `prev_raw`。

用 `10°→350°` 和 `350°→10°` 两组情况检查 `k` 的变化方向，再换成 rad 放进实际程序。

## 4. 完成任务以后，程序中的几类职责已经很清楚

做到这里，不需要为了“工程化”凭空发明很多类。先按数据经过的顺序整理程序即可：

```text
按键 / 当前状态
        ↓
目标生成
q_des(t), dq_des(t)
        ↓
关节控制
q / dq / q_des / dq_des → tau 或关节侧命令
        ↓
电机换算
减速比、offset、单圈编码器处理
        ↓
MuJoCo 或电机 SDK
```

仿真里，最后一层主要是 `data.ctrl` 和 `mj_step()`；实体程序里，最后一层是 SDK 的命令和反馈。前面的目标和关节语义可以保持一致。

实际完成任务时，可以按依赖顺序推进：先整理 joint/actuator 映射并跑通阻尼，再完成连续站立；实体部分先读懂 SDK 示例中的状态和命令字段，再写关节侧与电机侧的换算，完成缓慢回零和键盘目标，最后加入软件零位和单圈跳变处理。

到这里，第三次培训里的控制、机械结构和代码已经接到同一条实际运行链上。后续继续增加功能时，也可以沿这条链判断新的数据应该在哪一层产生、转换和使用。
